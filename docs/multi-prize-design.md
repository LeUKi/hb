# 多次领奖的代码判定红包（2026-10-30，第 7 条，设计稿，待用户看）

用户 2026-10-29 说“我现在只是在畅想”：代码判定作为全新的红包形态，能不能一个人领好几次；由判定器决定还能不能接着玩；比如大家一起刮一张刮刮乐，刮完一张换下一张，格子里可以有负数、多给几次机会、炸弹（扣一次机会、换一张卡）；也许最后一起结算，红包结束或者判定器结束了这个人时，把他赢的加起来发。用户担心：和现在“每人领一次、份数等于领到的人数”冲突；结算时领到的人可能比份数多；是不是要大改，还是做成新玩法。又问：判定器能不能控制玩家提交的频率。

这一份只出设计，不做。看过、定了第 7 节，再拆成几步。

## 0 现在的规则（[programmable-hongbao-design](programmable-hongbao-design.md) 第 2、3 节）

- 每人只能领到一次；领到了就走不到判定器。
- 每次领到就是一份：份数、每份至少、最后一份发完剩下的。
- 判定器返回 `ok`、`amount`、`message`、`state`；`state` 是整个红包共用的一份，最大 16 KB。
- 平台的尝试间隔（全站每个账号，红包页默认 2 秒）和人机验证在判定器前面。

## 1 要的是什么

- 一个人能在同一个红包里赢好几次，赢的钱可以是正的，也可以是负的（只能扣还没发的，见第 3 节）。
- 判定器决定这个人还能不能接着玩（比如没机会了、踩到炸弹出局了）。
- 每个人有自己的状态（剩几次机会、在刮哪张卡），不挤在共用的 16 KB 里。
- 判定器能比平台更严地限制频率（比如每人 10 秒一次），但不能比平台松。

## 2 结算：定了（2026-10-30）

用户逐个谈，第 1 个定的是“先记账，由判定器决定什么时候结算”（对话里的方向三），并说：

- 另开一张表，改动就不会很大；
- 每人只能最终结算一次，中途的都算待结算；
- 玩的人看得到中途每一次加减；
- 判定器可以在中途说“现在给这个人结算”，不说的由红包站在最后统一结算。

照这个，规则是：

- **每次判定**：判定器给这个人加或减（可以是 0），记进他的待结算；扣到 0 为止，不往回拿已经发出的钱（也没有已经发出的钱：结算前一分钱都不发）。
- **玩的人看到的**：每次的回复旁边写“+0.50，待结算 1.20”；“我的提交”里每一次都写这次加减多少、之后待结算多少。
- **结算，只有一次**：
  - 判定器在某次判定里说“结算这个人”：这次的加减先记上，然后把他的待结算一次发给他；从此他不能再提交；
  - 红包结束时（到时间、判定器结束了红包、发红包的人提前结束），还没结算的人由红包站统一结算。
- **结算就是一份**：每人结算时生成一条领取记录，金额是他的待结算；待结算是 0 的不生成。名单、排行榜、红包记录照旧按“一人一份”算。
- **存哪**：另开一张按人的表，放每个人的待结算、什么时候结算、结算多少和对应的领取记录；每次加减和之后的待结算记在那一次判定的记录上。现有“一人一份”的领取规则不动。

第 2 个（同一天）：**份数、每人最多都不要**，平台不加这些限制；每人最多这类规则判定器自己写就行。平台只剩“总奖池”这一个限制。用户还要：兼容旧的判定器（不带新字段就是当场结算，带上某个字段才是能赢好几次的玩法），旧的平均分钱函数要有说法，并且只要一种结算方式（第 2.3 节，待定）。

第 3 个（同一天）：**份数彻底拿掉**（对话里的方向 B），不给判定器留“声明份数”的路：加回份数就会有“份数满了奖池还没发完”这类边缘情况。旧代码的兼容由用户提的办法解决，细节按建议定了：

- **缺省 n**：分钱函数改成带份数 `even(n)`、`lucky(kind, n)`；不传 n 时 n = 总奖池（按 LDC 算）取整，最少 1，也就是“每份约 1 LDC”。`npm run check` 和部署时对没传 n 的提醒一句。
- **`even(n)`**：剩余奖池 ÷ (n − 已经结算的人数)，最少除以 1。就是原来的公式，把剩余份数换成“n 减去已经结算的人数”，会自己匀开。`lucky(kind, n)` 同样替换。
- **旧代码直接读的值**：`hongbao.count` 给缺省 n；`minEach` 给 1（0.01）；`remainingCount` 给 n 减去已经结算的人数，最少 1；`share` 给最少 0.01、最多奖池里还没被占的，`last` 一律 false。
- **跟着改的**：表单只填总奖池；判定器声明的份数、每份至少不再起作用；红包皮写“奖池还剩 x LDC”，名单不写几份里的几份；SDK 的 `shares` 给 null；奖池全部结算出去时自动结束，没发完的照提前结束退回；已经开放的红包照开放时的规则跑完。
- **代价**：以前分得很碎的旧判定器，不传 n 时行为会变（比如 1 LDC 分 10 份，现在第一个人拿走全部），作者要改成传 n 或做成参数。

第 4 个（同一天，按建议）：**判定器的写法**。

- 新玩法用两个新字段：`add`（这次加减多少，整数分，可以是负数，不写就是 0）和 `settle: true`（现在给这个人结算，可以和这次的 `add` 一起写）。
- 旧写法只是简写：`{ ok: true, amount: X }` 等于 `{ add: X, settle: true }`；`{ ok: false }` 等于什么都不加、不结算。
- 一个判定里不能同时写 `ok` 和 `add`，写了算出错，测试里也不通过。
- 平台先把旧写法翻译过来，后面只有一套算法：加减；扣到 0 为止；加的不超过奖池里还没被占的；要结算就结算。
- 结算时这个人还没结算的钱是 0：不生成领取记录，他也不能再玩。
- 判定器能读到这个人还没结算的钱 `player.pending`，和奖池里还没被占的 `hongbao.unclaimed`。

第 5 个（同一天，按建议）：**每个人自己的状态**。

- 判定时传进来 `player.state`（这个人上次存的，最开始是 null）；返回 `player: { … }` 就整个换掉，不写就不变，和共用的 `state` 一样。每人最大 4 KB，存在按人的那张表上。
- 共用的 `state` 照旧，放全场共享的东西（当前这张卡、刮开了哪些格子）。
- 只有判定器看得到；发红包的人下载的判定数据里有，开发包能重放。
- 当场结算的玩法也能用（比如记住这个人猜过哪些数）；旧判定器不写就没有。

第 6 个（同一天，按建议）：**玩的人在红包页上看到什么**。

- 每次提交后，判定器的回复后面平台加一行“+0.50 · 待结算 1.20 LDC”（扣钱写“−0.20 · 待结算 1.00 LDC”，加 0 不写）。
- 我的提交：每一次右边写这次加减和之后的待结算，比如“+0.50 → 1.20”。
- 我的结果：还没结算写“待结算 1.20 LDC · 判定器结算或红包结束时发”；结算以后同现在“已领取 1.20 LDC”；结算时是 0 写“没有领到”。
- 红包皮的提示：还没玩同现在；玩过、还没结算写“点「开」接着玩”；结算以后同现在领过的样子。
- 红包皮的奖池：“奖池还剩 12.50 LDC”，是总奖池减去已经结算的和大家还没结算的。
- 大家的待结算不公开：每人只看得到自己的；名单只列已经结算的人和金额；正在玩的人只在“挑战”里。想要比分榜的玩法，判定器用公开数据和动态自己做。

第 7 个（同一天，按建议）：**发红包的人**。

- 判定记录：时间线每行多写这次加减和之后的待结算（“+0.50 → 1.20”）；按人每人写“待结算 1.20”或“已结算 1.20”；顶上多一个“待结算 x LDC”。
- 不能手动给某一个人结算，只有判定器和红包站能结算；判定器卡住的，红包结束时统一结算兜底。
- 提前结束照现在的规则：有人赢到过钱（待结算大于 0 或者已经结算过）就不能提前结束；判定器连续出错暂停以后可以，提前结束时所有人按待结算统一结算，剩下的退回。

下面第 2.1、2.2 节是谈之前的两种做法，留着备查。

## 2 两种结算（谈之前）

### 2.1 赢一次发一次

- 每次判定器说“赢 0.30”，马上发一份。一个人能领好几份。
- 好处：领的人马上看到钱，和现在一样。
- 难处：
  - 负数格子扣不了：已经发出去的钱拿不回来，只能不发。
  - “每人领一次”是数据库的规则（一人一份的唯一约束），领取记录、名单、排行榜、称号（手气王等）都按“一人一份”算，要大改。
  - 份数没法预先定：赢几次都不知道。

### 2.2 记账，最后一起结算（建议）

- 每次判定器说“加 0.30”“减 0.10”，只记在这个人的**待结算**上，不发钱。
- 结算的时候，每人的待结算一次发完，**一人一份**：
  - 红包结束（到时间、判定器结束了红包、红包作者提前结束）时，所有人一起结算；
  - 判定器说这个人“出局”或“收手”（第 4 节的 `done`），他马上结算，之后不能再玩。
- 好处：
  - 负数格子好办：只从待结算里扣，扣到 0 为止，钱从来不用往回拿。
  - “一人一份”不变：结算时每人一条领取记录，名单、排行榜、领取记录照旧能用。用户担心的“结算时领到的人比份数多”，在这种做法里份数换成别的意思（第 3 节）。
- 难处：领的人要等结算才拿到钱；红包页要把“待结算”写清楚。

建议 2.2。它也正好是用户想到的“最后统一结算”。

## 3 钱怎么算（按 2.2）

- **总奖池**照旧开放前定好、锁定（🐟额红包从🐟额锁定）。
- **不再有份数和每份至少**。换成两个：
  - 每人最多（选填）：一个人的待结算最多到多少，到了就不再加；
  - 结算最少 0.01：待结算不到 0.01 的人不结算（等于没领到）。
- **不会超出奖池**：所有人待结算加起来，任何时候都不超过总奖池。判定器“加”的时候，平台按“奖池里还没被待结算占住的”拉进范围（多了封顶，同现在的“按上限发”）；传给判定器的 `hongbao.unclaimed` 就是这个数。
- **负数**：只从这个人自己的待结算里扣，扣到 0 为止；扣下来的回到奖池，别人还能赢。
- **结算以后**：没被占住的钱照提前结束退回🐟额。
- **先只用🐟额**：结算时可能一下子要给很多人发钱。🐟额是站内记账，一批语句就能发完；商户直发要一笔一笔调用 LINUX DO Credit，量大了慢、也容易半途出错。建议多次领奖先只支持从🐟额发。

## 4 判定器怎么写（协议第五版，草案）

- 判定器要自己声明它是多次领奖的：`export const meta = { ..., multi: true }`。发红包时选了这样的判定器，红包就是多次领奖的；不是发红包的人另开的开关（判定器得照这个写，换不了）。
- 传进去的多两样：
  - `player`：这个人自己的状态（判定器上次存的，最开始 null，最大 4 KB），和他的待结算 `pending`（分）；
  - `hongbao.unclaimed`：奖池里还没被待结算占住的。
- 返回的多三样，原来的 `ok`、`amount` 在多次领奖里不用：
  - `add`：这次加多少（分，可以是负数，0 就是没输没赢）；
  - `player`：写了就整个换掉这个人的状态；
  - `done`：`true` 就是这个人到此为止（出局或者收手），马上结算。
- `message`、`state`（共用的）、`view`、`announce`、`end` 照旧。
- 例子“大家一起刮”：共用的 `state` 记当前这张卡；`player` 记这个人剩几次机会；刮到 +0.50 就 `add: 50`，刮到 −0.20 就 `add: -20`，刮到“再来两次”就把机会 +2 写回 `player`，踩到炸弹就机会 −1、换一张卡（共用 `state`），机会用完就 `done: true`。
- 开发包的模拟、测试、重放都要跟着支持 `player`、`add`、`done`，测试里能写“结算后每人拿到多少”。

## 5 频率

- 平台的尝试间隔照旧在前面，判定器改不了、更松不了。
- 判定器自己可以更严：`player` 里记上次的时间，`now` 不到 10 秒就返回“10 秒后再刮”（`add: 0`）。这一次照样算被判定过一次。现在的协议就能这样写（用 `state` 按人记），多次领奖以后用 `player` 更省地方。

## 6 页面

- **红包页**：自己的结果写“待结算 1.20 LDC · 红包结束时一起发”；出局或收手的写“已结算 1.20 LDC”。玩法那一行写“多次领奖：每次的输赢先记着，结束时一起发”。
- **名单**：结束前写“N 人在玩”，不列金额（金额还没定）；结算后照现在的名单列每人结算多少。
- **判定记录**（第 6 条，[judge-records-design](judge-records-design.md)）：每一次写“+0.50”“−0.20”和那一刻的待结算。
- **排行榜、称号**：按结算的金额算，和现在一样；“手速王”这类按领取时间的称号，多次领奖的红包不评。
- **发红包表单**：选了多次领奖的判定器，发多少一步只有总奖池和每人最多；下面一句“每次的输赢先记着，红包结束或判定器让这个人出局时一起发，只能从🐟额发。”。

## 7 要用户定的（第 1 条已定，见第 2 节开头）

1. 结算：最后一起结算（建议），还是赢一次发一次。
2. 先只支持从🐟额发（建议）。
3. 由判定器声明是多次领奖的（建议），还是发红包的人自己开。
4. 份数换成“每人最多”（选填）：行不行。
5. 负数只扣待结算、扣到 0 为止：用户已经这么想，照这个写了。
6. 要不要让领的人自己“收手”（不玩了，马上结算）：建议由判定器决定，比如约定输入“收手”就 `done: true`；平台不另做按钮。

## 8 改动有多大

- 协议第五版（判定器、开发包、模拟、重放、测试格式）。
- 服务器：一张按人的待结算表（和 [judge-records-design](judge-records-design.md) 第 4 节的按人汇总表可以是同一张），判定时更新；结算（结束时一批、出局时一条）；奖池占用的检查。
- 页面：红包页、名单、表单、判定记录。
- 不动经典玩法和单次领奖的代码判定红包。
