# 多次领奖的代码判定红包（2026-10-30，第 7 条，设计稿，待用户看）

用户 2026-10-29 说“我现在只是在畅想”：代码判定作为全新的红包形态，能不能一个人领好几次；由判定器决定还能不能接着玩；比如大家一起刮一张刮刮乐，刮完一张换下一张，格子里可以有负数、多给几次机会、炸弹（扣一次机会、换一张卡）；也许最后一起结算，红包结束或者判定器结束了这个人时，把他赢的加起来发。用户担心：和现在“每人领一次、份数等于领到的人数”冲突；结算时领到的人可能比份数多；是不是要大改，还是做成新玩法。又问：判定器能不能控制玩家提交的频率。

这一份只出设计，不做。看过、定了第 7 节，再拆成几步。

## 0 现在的规则（[programmable-hongbao-design](programmable-hongbao-design.md) 第 2、3 节）

- 每人只能领到一次；领到了就走不到判定器。
- 每次领到就是一份：份数、每份至少、最后一份发完剩下的。
- 判定器返回 `ok`、`amount`、`message`、`state`；`state` 是整个红包共用的一份，最大 16 KB。
- 平台的尝试间隔（全站每个账号，红包页默认 2 秒）和人机验证在判定器前面。

## 1 要的是什么

- 一个人能在同一个红包里赢好几次，赢的钱可以是正的，也可以是负的（只能扣还没发的，见第 3 节）。
- 判定器决定这个人还能不能接着玩（比如没机会了、踩到炸弹出局了）。
- 每个人有自己的状态（剩几次机会、在刮哪张卡），不挤在共用的 16 KB 里。
- 判定器能比平台更严地限制频率（比如每人 10 秒一次），但不能比平台松。

## 2 两种结算

### 2.1 赢一次发一次

- 每次判定器说“赢 0.30”，马上发一份。一个人能领好几份。
- 好处：领的人马上看到钱，和现在一样。
- 难处：
  - 负数格子扣不了：已经发出去的钱拿不回来，只能不发。
  - “每人领一次”是数据库的规则（一人一份的唯一约束），领取记录、名单、排行榜、称号（手气王等）都按“一人一份”算，要大改。
  - 份数没法预先定：赢几次都不知道。

### 2.2 记账，最后一起结算（建议）

- 每次判定器说“加 0.30”“减 0.10”，只记在这个人的**待结算**上，不发钱。
- 结算的时候，每人的待结算一次发完，**一人一份**：
  - 红包结束（到时间、判定器结束了红包、红包作者提前结束）时，所有人一起结算；
  - 判定器说这个人“出局”或“收手”（第 4 节的 `done`），他马上结算，之后不能再玩。
- 好处：
  - 负数格子好办：只从待结算里扣，扣到 0 为止，钱从来不用往回拿。
  - “一人一份”不变：结算时每人一条领取记录，名单、排行榜、领取记录照旧能用。用户担心的“结算时领到的人比份数多”，在这种做法里份数换成别的意思（第 3 节）。
- 难处：领的人要等结算才拿到钱；红包页要把“待结算”写清楚。

建议 2.2。它也正好是用户想到的“最后统一结算”。

## 3 钱怎么算（按 2.2）

- **总奖池**照旧开放前定好、锁定（🐟额红包从🐟额锁定）。
- **不再有份数和每份至少**。换成两个：
  - 每人最多（选填）：一个人的待结算最多到多少，到了就不再加；
  - 结算最少 0.01：待结算不到 0.01 的人不结算（等于没领到）。
- **不会超出奖池**：所有人待结算加起来，任何时候都不超过总奖池。判定器“加”的时候，平台按“奖池里还没被待结算占住的”拉进范围（多了封顶，同现在的“按上限发”）；传给判定器的 `hongbao.unclaimed` 就是这个数。
- **负数**：只从这个人自己的待结算里扣，扣到 0 为止；扣下来的回到奖池，别人还能赢。
- **结算以后**：没被占住的钱照提前结束退回🐟额。
- **先只用🐟额**：结算时可能一下子要给很多人发钱。🐟额是站内记账，一批语句就能发完；商户直发要一笔一笔调用 LINUX DO Credit，量大了慢、也容易半途出错。建议多次领奖先只支持从🐟额发。

## 4 判定器怎么写（协议第五版，草案）

- 判定器要自己声明它是多次领奖的：`export const meta = { ..., multi: true }`。发红包时选了这样的判定器，红包就是多次领奖的；不是发红包的人另开的开关（判定器得照这个写，换不了）。
- 传进去的多两样：
  - `player`：这个人自己的状态（判定器上次存的，最开始 null，最大 4 KB），和他的待结算 `pending`（分）；
  - `hongbao.unclaimed`：奖池里还没被待结算占住的。
- 返回的多三样，原来的 `ok`、`amount` 在多次领奖里不用：
  - `add`：这次加多少（分，可以是负数，0 就是没输没赢）；
  - `player`：写了就整个换掉这个人的状态；
  - `done`：`true` 就是这个人到此为止（出局或者收手），马上结算。
- `message`、`state`（共用的）、`view`、`announce`、`end` 照旧。
- 例子“大家一起刮”：共用的 `state` 记当前这张卡；`player` 记这个人剩几次机会；刮到 +0.50 就 `add: 50`，刮到 −0.20 就 `add: -20`，刮到“再来两次”就把机会 +2 写回 `player`，踩到炸弹就机会 −1、换一张卡（共用 `state`），机会用完就 `done: true`。
- 开发包的模拟、测试、重放都要跟着支持 `player`、`add`、`done`，测试里能写“结算后每人拿到多少”。

## 5 频率

- 平台的尝试间隔照旧在前面，判定器改不了、更松不了。
- 判定器自己可以更严：`player` 里记上次的时间，`now` 不到 10 秒就返回“10 秒后再刮”（`add: 0`）。这一次照样算被判定过一次。现在的协议就能这样写（用 `state` 按人记），多次领奖以后用 `player` 更省地方。

## 6 页面

- **红包页**：自己的结果写“待结算 1.20 LDC · 红包结束时一起发”；出局或收手的写“已结算 1.20 LDC”。玩法那一行写“多次领奖：每次的输赢先记着，结束时一起发”。
- **名单**：结束前写“N 人在玩”，不列金额（金额还没定）；结算后照现在的名单列每人结算多少。
- **判定记录**（第 6 条，[judge-records-design](judge-records-design.md)）：每一次写“+0.50”“−0.20”和那一刻的待结算。
- **排行榜、称号**：按结算的金额算，和现在一样；“手速王”这类按领取时间的称号，多次领奖的红包不评。
- **发红包表单**：选了多次领奖的判定器，发多少一步只有总奖池和每人最多；下面一句“每次的输赢先记着，红包结束或判定器让这个人出局时一起发，只能从🐟额发。”。

## 7 要用户定的

1. 结算：最后一起结算（建议），还是赢一次发一次。
2. 先只支持从🐟额发（建议）。
3. 由判定器声明是多次领奖的（建议），还是发红包的人自己开。
4. 份数换成“每人最多”（选填）：行不行。
5. 负数只扣待结算、扣到 0 为止：用户已经这么想，照这个写了。
6. 要不要让领的人自己“收手”（不玩了，马上结算）：建议由判定器决定，比如约定输入“收手”就 `done: true`；平台不另做按钮。

## 8 改动有多大

- 协议第五版（判定器、开发包、模拟、重放、测试格式）。
- 服务器：一张按人的待结算表（和 [judge-records-design](judge-records-design.md) 第 4 节的按人汇总表可以是同一张），判定时更新；结算（结束时一批、出局时一条）；奖池占用的检查。
- 页面：红包页、名单、表单、判定记录。
- 不动经典玩法和单次领奖的代码判定红包。
