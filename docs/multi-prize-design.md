# 能赢好几次的代码判定红包（2026-10-30，第 7 条，设计稿）

用户 2026-10-29 说“我现在只是在畅想”：代码判定红包能不能让一个人领好几次，由判定器决定还能不能接着玩，比如大家一起刮刮乐，格子里有加钱、扣钱、多给几次机会、炸弹；最后一起结算。2026-10-30 逐个谈定了下面的规则（第 7 节是谈的经过）。

这一份是设计稿，还没开始做。

## 1 一句话规则

**每个人在一个红包里最后只结算一次。每次判定，判定器说给他加或减多少；判定器说“结算”，或者红包结束，他那时的钱一次发给他。**

以前的“领到一份”就是这条规则的特例：加完马上结算。旧判定器不用改，照旧这样跑。

## 2 钱

- **只有总奖池一个限制**。不再有份数、每份至少、最后一份发完剩下的；“每人最多赢多少”这类规则判定器自己写。
- **待结算**：每个人有一笔还没结算的钱（待结算），从 0 开始。
  - 判定器每次给他加或减（整数分，可以是负数）。
  - 扣到 0 为止。结算前一分钱都不发，所以不存在“把发出去的钱扣回来”。
  - 加的时候不能超过奖池里还没被占的：总奖池减去已经结算的，再减去大家的待结算。超出的部分加不上。
  - 扣掉的钱回到奖池，别人还能赢。
- **结算，每人只有一次**：
  - 判定器在某次判定里说“结算”（可以是给这次提交的人，也可以是给同桌的人，见第 3.3 节），这个人的待结算一次发给他，从此不能再提交；
  - 红包结束时（到截止时间、判定器结束了红包、发红包的人提前结束），还没结算的人由红包站统一结算；
  - 结算就是一份：生成一条领取记录，金额是他的待结算。是 0 的不生成。名单、排行榜、红包记录都照“一人一份”算。
- **什么时候结束**：
  - **奖池空了就马上结束并结算**：奖池里没被占的变成 0（已经结算的加上大家的待结算，等于总奖池），红包马上结束，所有还没结算的人一起结算。不会出现“奖池被赢满了还开着”。
  - 或者到截止时间；或者判定器结束红包；或者发红包的人提前结束（规则见 4.2）。
  - 没发完的钱照提前结束的规则退回。
- **红包结束时的统一结算**：可能有几千个人，分批做；断了能接着做，重复做不会重复发钱。这期间红包显示“结算中”，名单陆续出现，同现在的“开奖中”。
- **站长停用**：先给所有人按待结算统一结算（玩的人没做错什么），剩下的再退回发红包的人。
- **发红包的人自己也能玩**：同现在的自领，结算时不付款，钱留在奖池，称号是“自领的屑”。他在判定记录里看得到别人只给自己看的数据，这一点照实写在帮助页上，不另加限制。
- **从哪发**：🐟额和商户直发都行。商户直发的奖池不锁定，结算时每人付一笔（同现在每份一笔）；红包结束统一结算时可能一下子付很多笔，商户余额不够的那几笔照现在的规则算“未发出”。
- **已经开放的红包**：照它们开放时的份数规则跑完，不受影响。上线后有一段时间两套规则并存，直到最后一个旧红包结束。
- **草稿里已经填了份数的代码判定红包**：开放时按新规则，份数作废；打开这类草稿时，表单上说一句“新规则下不再有份数，只按总奖池”。

## 3 判定器怎么写（协议第 5 版）

### 3.1 传进去的

在现在的 `submission` 上多这些：

- `player.pending`：这个人现在的待结算（分）。
- `player.state`：这个人自己的状态，判定器上次给他存的，最开始是 null。最大 4 KB，只有判定器看得到。
- `player.view`：只给这个人看的数据，判定器上次给他存的（见 3.4）。
- `hongbao.unclaimed`：奖池里还没被占的（分）。

共用的 `state`（整个红包一份，最大 16 KB）照旧，放全场共享的东西，比如当前这张卡、每一桌的牌。

### 3.2 返回的

| 字段 | 意思 |
|---|---|
| `add` | 给这次提交的人加多少，整数分，可以是负数；不写就是 0 |
| `settle: true` | 现在给这次提交的人结算（可以和这次的 `add` 一起写） |
| `player: { state, view }` | 这次提交的人自己的状态、只给他看的数据；写了哪样就整个换掉哪样，不写不变 |
| `others: [{ id, add, settle, state, view }]` | 给别人的，见 3.3 |
| `message`、`state`、`view`、`announce`、`end` | 照旧：给他的回复、共用的状态、公开数据、一条动态、结束红包 |

- **旧写法只是简写**：`{ ok: true, amount: X }` 等于 `{ add: X, settle: true }`；`{ ok: false }` 等于什么都不加、不结算，接着能试。
- 一个判定里不能同时写 `ok` 和 `add`，写了算出错，测试里也不通过。
- 平台先把旧写法翻译过来，后面只有一套算法：加减；扣到 0 为止；加的不超过奖池里还没被占的；要结算就结算。
- 结算时这个人的待结算是 0：不生成领取记录，他也不能再提交。
- 判定记录记下每一次的加减、结算、`others` 写给别人的东西、个人状态和只给他看的数据，开发包能重放，结束后公开代码时核对得上。

### 3.3 同桌的人：`others`

多人一起玩（斗地主、拼桌）时，一次判定要影响好几个人：小红出了最后一手牌，三家要一起结算；小红出牌后，另外两家看到的“上家出了什么”要跟着变。

- `others` 是一个列表，每一项是一个人：`id`（LINUX DO 数字 ID，同 `submission.user.id`），加上 `add`、`settle`、`state`、`view`，意思同上面给自己的。
- **只能写给**：在这个红包里被判定过的、还没结算的、在领取范围以内的人。不能凭空给一个没来过的人加钱。不能写给自己（自己的用上面那几项）。
- 一次最多 10 个人。
- 每一项也能带一句 `message`，给那个人看：比如小红出了一张牌，小明的待结算少了 0.20，推给小明的是“小红这一步：−0.20，待结算 1.00 LDC”，后面跟判定器写给他的那句话。
- 判定器读不到别人的 `player.state` 和 `player.view`。要互相看的东西（比如三家的手牌），放在共用的 `state` 里；写给别人的 `state`、`view` 是整个换掉。

### 3.4 只给这个人看的数据：`view`

公开数据（`view`）所有人都看得到；这一份只给这个人看，比如他的手牌、他还剩几次机会。

- 样子同公开数据：`{ summary, data }`。`summary` 最多 200 个字，纯文字，红包页上画出来；`data` 是任意 JSON，最大 4 KB，给附带网页用。
- 红包页上，他自己在“我的结果”上面看到 `summary`；变了就推送过来，不用刷新、不用再提交。
- 附带网页用 SDK 读：`hb.myView()` 读，`hb.on("myView", fn)` 订阅变化。
- 别人看不到。发红包的人在下载的判定数据里看得到（同所有判定记录），所以作者自己上桌不公平，帮助页要写清楚。

### 3.5 分钱函数和旧字段

- 分钱函数改成带份数：`tools.money.even(n)`、`tools.money.lucky(kind, n)`。
- 不传 n 时，n = 总奖池（按 LDC 算）取整，最少 1，也就是“每份约 1 LDC”。`npm run check` 和部署时对没传 n 的提醒一句。
- `even(n)` = 剩余奖池 ÷ (n − 已经结算的人数)，最少除以 1。就是原来的公式，把剩余份数换成“n 减去已经结算的人数”，会自己匀开。`lucky(kind, n)` 同样替换。
- 旧代码直接读的值给兼容值：

| 字段 | 以前 | 第 5 版 |
|---|---|---|
| `hongbao.count`（总份数） | 发红包时填的份数 | 缺省 n |
| `hongbao.minEach`（每份至少） | 发红包时填的 | 1（0.01） |
| `hongbao.remainingCount`（剩余份数） | 还剩几份 | n 减去已经结算的人数，最少 1 |
| `share.min` / `share.max` | 每份至少 / 给后面留够以后的上限 | 0.01 / 奖池里还没被占的 |
| `share.last` | 最后一份发完剩下的 | 一律 false |

- `even(n)` 里“已经结算的人数”只算真拿到钱的人，结算 0 的不算。
- **代价**：以前把奖池分得很碎的旧判定器，不传 n 时行为会变（比如 1 LDC 分 10 份，现在第一个人拿走全部）。作者要改成传 n，或者把份数做成参数。

### 3.6 旧判定器

协议第 1 到第 4 版的判定器叫“旧判定器”。

- 已经开放的红包照旧跑完。
- **用来发新红包之前，要按新规则重新跑一遍测试**（不算部署次数），通过了才能用。按旧规则写的断言（比如“最后一份领到多少”）在新规则下会不通过，作者改代码或测试，再部署新版本。
- 标注清楚：判定器页、判定器广场的卡片、发红包挑判定器的弹窗上，旧判定器带标签“旧判定器”，说明“按旧规则（有份数）写的判定器，要按新规则重新跑一遍测试才能发新红包。”；自己的判定器页上，旧版本旁边是“按新规则重新跑测试”。
- 别人的旧判定器在作者更新以前，不能用来发新红包；卡片上的“用它发红包”换成“作者还没按新规则更新”。
- 判定器声明里的份数、每份至少的默认值和范围作废。

### 3.7 频率

平台的尝试间隔照旧在前面，判定器改不了、更松不了。判定器自己可以更严：在 `player.state` 里记上次的时间，`now` 不到 10 秒就回复“10 秒后再来”（`add` 不写）。没有定时器：轮到某人却不动，等下一个人提交时，判定器按 `now` 判断超时、替他处理。

## 4 页面

### 4.1 玩的人

- 每次提交后，判定器的回复后面，平台加一行“+0.50 · 待结算 1.20 LDC”（扣钱写“−0.20 · 待结算 1.00 LDC”，加 0 不写）。
- “我的提交”改叫“我的记录”：每一次右边写这次加减和之后的待结算，比如“+0.50 → 1.20”。别人通过 `others` 改到他的那一步也在里面，写清是谁的哪一步，比如“小红出牌 · −0.20 → 1.00”。
- 只给他看的数据（3.4）：`summary` 在“我的结果”上面，变了就更新。
- 我的结果：还没结算写“待结算 1.20 LDC · 判定器结算或红包结束时发”；结算以后同现在“已领取 1.20 LDC”；结算时是 0 写“没有领到”。
- 红包皮的提示：还没玩同现在；玩过、还没结算写“点「开」接着玩”；结算以后同现在领过的样子。
- 红包皮的奖池：“剩 3 份”换成“奖池还剩 12.50 LDC”，是总奖池减去已经结算的和大家的待结算。
- 大家的待结算不公开：每人只看得到自己的；名单只列已经结算的人和金额；正在玩的人只在“挑战”里。想要比分榜的玩法，判定器用公开数据和动态自己做。

### 4.2 发红包的人

- 发红包表单：代码判定红包只填总奖池，不再有份数和每份至少；判定器声明的份数、每份至少的默认值和范围不再起作用。
- 判定记录：时间线每行多写这次加减和之后的待结算（“+0.50 → 1.20”）；按人每人写“待结算 1.20”或“已结算 1.20”；顶上多一个“待结算 x LDC”。
- 不能手动给某一个人结算，只有判定器和红包站能结算；判定器卡住的，红包结束时统一结算兜底。
- 提前结束照现在的规则：有人赢到过钱（待结算大于 0 或者已经结算过）就不能提前结束；判定器连续出错暂停以后可以，提前结束时所有人按待结算统一结算，剩下的退回。

### 4.3 实时推送

现在每个红包有一条推送通道，只在红包页上用（用户 2026-10-30：只有红包页有推送是合理的，其他页面照旧轮询）。这类玩法要的“推给某一个人”现在没有，先把通道整理一版（第 6 节的第 0 步）：

- **公开消息带序号**：通道里推给所有人的消息（红包的公开信息、已判定几次、公开数据、动态、在看的人数）都带这个红包内递增的序号，连上时第一条消息就告诉页面现在是第几号。页面发现序号跳了（中间漏了），就把红包的公开信息和动态整份重读一次。以后加新的公开消息，不用再单独想漏了怎么办。序号存在红包自己的 Durable Object 里，休眠醒来也接得上。
- **只推给这个人的消息**：新加一种，推给这个人开着的所有标签页和设备，写的是他这部分现在的样子：待结算、只给他看的数据、结算了没有和结算多少、最新的一条“我的提交”。他自己提交、别人通过 `others` 改到他、红包站给他结算，都会推。因为每次都是整份，漏了也不要紧，下一条就对上；重连时照现在一样把自己的那部分重读一次。现在的“付款状态变了，重新读”照旧。
- **判定相关的推送更快**：已判定几次、公开数据、动态，从最多每秒一次改成和红包公开信息一样，300 毫秒内的多次合成一次。回合制的玩法，对手出牌后差不多马上就能看到。
- 游客照旧轮询（他们没有只给自己的东西）；连接超过上限时照旧改成轮询。

### 4.4 附带网页 SDK

- 先做、不依赖这类玩法的三样（`hb.me()`、`hb.now()`、`hb.login()`），写在 [judge-page-design](judge-page-design.md) 11.12。
- 这类玩法再加：
  - `hb.me()` 多给待结算、结算了没有、结算多少；变了就推（4.3 的“只推给这个人的消息”）。
  - `hb.submit()` 的结果和 `hb.mine()` 的每一条，多写这次加减、之后的待结算、结算了没有；`hb.mine()` 也包括别人通过 `others` 改到他的那几条（同“我的记录”）。
  - `hb.myView()`、`hb.on("myView", fn)`：只给他看的数据（3.4）。

### 4.5 其他

- 小号不加新限制：平台不默认收紧，判定器也不声明建议的领取范围；靠现有的领取范围、领取前人机验证和尝试间隔，由发红包的人自己设。
- 领取前人机验证照现在：开了的，每次提交都要先过一次。
- 称号：手速王按“开放到领到用了多久”评，这类红包多数人在结束时才结算，不评；手气王、手气亡、自领的屑照常。
- 显示份数的地方都换掉：红包皮写“奖池还剩 x LDC”；红包广场的卡片、论坛里的红包图、分享文字、红包记录里的“已领 3/5”换成“奖池还剩”或“已发出 x LDC”。
- SDK 的 `hongbao.shares` 对代码判定红包给 null。

## 5 例子

### 5.1 大家一起刮刮乐

红包：总奖池 20 LDC，截止 3 天。判定器：共用的 `state` 放当前这张 5×5 的卡；每人开始 3 次机会，刮一格用 1 次，炸弹再扣 1 次并换卡。

1. 小明刮到 +0.50：`{ add: 50, player: { state: { tries: 2 } } }`。他看到“+0.50 · 待结算 0.50 LDC”，奖池还剩 19.50。
2. 小明刮到 −0.20：`{ add: -20, player: { state: { tries: 1 } } }`。待结算 0.30，扣掉的回到奖池。
3. 小红刮到“再来两次”：`{ player: { state: { tries: 4 } } }`。
4. 小明踩到炸弹：`{ player: { state: { tries: 0 } }, state: 新卡, settle: true }`。机会用完，判定器顺手结算，小明领到 0.30，之后不能再提交。
5. 小红输入“收手”：`{ settle: true }`，按她的待结算结算。
6. 奖池被占满：没被占的变成 0 的那一刻，红包马上结束，所有还没结算的人一起结算。
7. 三天到了：还没结算的人由红包站统一结算，剩下的退回。

### 5.2 斗地主，人齐开桌，只玩一局

- 输入“排队”进队列；第三个人排上时，判定器洗牌发牌，三家的手牌放在共用的 `state` 里，再用 `others` 和 `player` 给三个人各写一份只给自己看的数据：“你的手牌：……，轮到小红叫地主”。
- 轮到谁，谁输入“叫”“不叫”“3 3 3 4”“不要”；判定器检查轮次和牌型，用 `others` 更新另外两家看到的“上家出了什么”。
- 最后一手牌出完，判定器在这一次判定里给三家一起加减并结算：赢的加、输的不加（只玩一局，待结算从 0 开始，没有可扣的），`others` 里两个人加上自己，一共三个人一起结算。
- 有人一直不出牌：同桌任何人提交时，判定器发现他超过 60 秒没动，替他“不要”或判他输。
- 公开数据写每一桌的进度（“第 3 桌：小明、小红、小刚，轮到小红”），附带网页画出牌桌。

### 5.3 用旧判定器发 20 LDC

它是旧判定器，先要按新规则重新跑一遍测试（3.6）。代码是 `{ ok: true, amount: tools.money.even() }`，等于“加完当场结算”。缺省 n = 20，第一个人拿 20 ÷ 20 = 1.00，之后每人 1.00，20 个人正好发完，红包自动结束。和以前“20 LDC 分 20 份”一样。

## 6 改动范围

- **协议第 5 版**：运行时传入 `player`、`hongbao.unclaimed`，读 `add`、`settle`、`player`、`others`；分钱函数带 n；旧字段的兼容值。开发包的测试格式（`tests.json` 能断言 `add`、`settle`、`player`、`others`、每人的待结算）、`simulate`、`replay`、`check` 跟着改。第 1 到第 4 版照旧。
- **服务器**：一张按人的表（待结算、个人状态、只给他看的数据、结算时间和对应的领取记录），可以在判定记录用的按人汇总表上扩；判定时在同一批语句里更新这个人和 `others` 里的人；结算生成领取记录和付款；红包结束时统一结算；奖池占用的检查；只给本人的推送。
- **推送**：公开消息带序号，只推给这个人的消息，判定相关的推送 300 毫秒合一次（4.3）。
- **页面**：指令框的加减一行、我的提交、我的结果、只给自己看的数据、红包皮的奖池、名单；发红包表单去掉份数和每份至少；判定记录的待结算；SDK 的 `hb.myView()`。
- **文档**：`/help/code`、开发包的 `AGENTS.md`、`/help/page`。
- **不动**：经典玩法；已经开放的代码判定红包。

建议分五步：第 0 步，整理推送通道（4.3，对现在的红包也有好处）→ 协议第 5 版和开发包（能在本地写、测这类玩法）→ 服务器的按人表、判定和结算 → 红包页、表单和判定记录 → 只给自己看的数据和 `others`、SDK。

## 7 谈的经过（2026-10-30，用户逐个定）

1. 结算：先记账，由判定器决定什么时候结算；另开一张表；每人只结算一次；玩的人看得到每一次加减；判定器可以中途结算，红包站最后兜底。
2. 份数、每人最多都不要，平台只剩总奖池。
3. 份数彻底拿掉（不给判定器留“声明份数”的路，免得“份数满了奖池还没发完”）；兼容旧代码用 `even(n)` 的缺省 n，“奖池数字取整，最少为 1”；`even(n)` 用旧公式。
4. 写法：`add`、`settle`，旧的 `ok` / `amount` 只当简写。
5. 每人自己的状态 `player.state`，最大 4 KB。
6. 玩的人看到的：待结算只有自己看得到，名单只列真发出去的钱。
7. 发红包的人看得到每个人的待结算，不能手动给某个人结算，提前结束照现在的规则。
8. 小号不加新限制（“这里不需要代码介入”）。
9. 🐟额和商户直发都行。
10. 用斗地主检验：补上 `others`（给同桌的人加减、结算、写状态和只给他看的数据）和只给这个人看的数据（用户：“这个很值得，我还以为已经有了”）。返回里给自己的状态和数据统一写成 `player: { state, view }`。
11. 推送：只有红包页有推送是合理的；公开消息带序号、加“只推给这个人”的消息、判定相关的推送改成 300 毫秒合一次，作为第 0 步。
12. 逐项对照现有功能找出的问题：
    - 发红包的人能玩（有“自领的屑”，不加复杂度）；
    - 奖池空了就马上结束并结算；
    - 人机验证不动，保持每次都验证；
    - 旧判定器要按新规则重跑测试才能发新红包，标注“旧判定器”（“目前没什么人开发，可以顶住整改压力”）；
    - 站长停用照发待结算；`others` 带一句话；“我的提交”改成“我的记录”；统一结算分批、显示“结算中”；不评手速王；显示份数的地方都换掉；判定记录能重放；`even(n)` 只算拿到钱的人；旧草稿的份数作废；两套规则并存到旧红包跑完。
