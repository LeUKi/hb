# 开奖证明：可验证的随机（2026-10-22 定）

带随机的红包，结果要能让任何人自己核对：抽到站长也好，抽到谁都好，能说清不是安排的。所有人看到的都一样，站长中奖没有任何特别的展示。

## 0 范围

| 红包 | 随机从哪来 | 什么时候出结果 | 能证明到什么程度 |
|---|---|---|---|
| 限时开奖 | 截止后的下一轮 drand 公开随机数 + 截止时的报名名单 | 截止后约 1–4 秒开奖 | 连本站也无法事先知道或挑选 |
| 拼手气 | 开放时的秘密种子，开放时公布封存值，结束后公开种子 | 领取时当场出 | 金额和顺序在开放时就定死，之后没改；每人拿的是他那个位置的那份 |
| 自定义金额（随机顺序） | 同拼手气，只打乱顺序 | 当场 | 同拼手气 |
| 固定均分、自定义金额（按顺序） | 没有随机 | 当场 | 不需要 |

- 用哪一版在开放时定下：这套上线以后开放的红包用新算法（下称 v2），以前开放的一律照旧，上线时还没截止的限时开奖也照旧。
- 拼手气不等 drand：领取当场出金额（用户定，2026-10-22，等几秒“不接受”）。代价见第 6 节。
- 不找第三方给时间盖章（用户定）。

## 1 说法

| 说法 | 意思 |
|---|---|
| drand | 多家机构联合运行的公共随机数，Cloudflare 是其中之一；quicknet 每 3 秒一轮，每轮带门限签名，谁都不能事先算出或改动 |
| 轮次 | drand 的第几轮，由时间算出，每轮的随机数产生后永远不变 |
| 名单哈希 | 截止时报名名单的指纹，名单改一个字就对不上 |
| 封存值 | 拼手气开放时公布的种子指纹，结束后公开种子，核对指纹就知道种子没换过 |
| 开奖证明 | 名单弹窗里的入口，和 🎲 页面上的全部数据 |

界面上写“drand 公开随机数”，不展开讲门限签名；🎲 页面写全。

## 2 公共的算法部分

- 所有哈希都是 SHA-256，十六进制小写。所有要哈希的文字都是 UTF-8，各项之间用换行（`\n`）分开，没有多余的空格和末尾换行，方便较真的人用 `printf … | sha256sum` 手算。
- **随机字节**：由种子 `seed`（64 位十六进制）依次算 `SHA-256("<seed>:0")`、`SHA-256("<seed>:1")`……，每块 32 字节，接成一条字节流，按顺序取用。
- **取整**：沿用现在的拒绝采样（`random-money.ts` 的 `randomIntegerInclusive`）：取够位数的字节，高位多余的位清零，按大端读成整数，超出范围就丢掉重取。不偏向任何结果。
- 抽人、生成金额、打乱顺序都沿用现在的算法（Floyd 抽样、二倍均值 / 初始均值上下 50%、Fisher–Yates 洗牌），只把字节来源从服务器随机数换成这条字节流。
- 服务器和浏览器用同一份实现（放在共享的 contracts 包里）；仓库里放几组固定的测试数据，服务器、浏览器和独立验证脚本都用它们测。算法以后要改就开新版本，旧版本永远保留，老红包要能一直被验证。

## 3 限时开奖（v2）

- **用哪一轮**：截止时刻（数据库时间）之后的下一轮，按 quicknet 的起始时间和 3 秒周期算出，开奖等 0–3 秒（用户定，2026-10-22：不另外多等），再加上节点发出这一轮的零点几秒。Worker 和 D1 的时间由 Cloudflare 校准，误差在毫秒级。提前截止（报名满了或发红包的人提前结束）一样，从实际截止的时刻算。
- **名单冻结**：截止时，报名名单按报名序号排好，每行 `序号:报名编号`，用换行连起来，算出名单哈希。名单哈希马上存下、实时推送给开着页面的人、显示在“怎么开奖”里，事后再改名单就对不上。用报名编号而不是用户名（会改）或数字 ID（不多公开个人信息）。
- **种子** = `SHA-256("hb.lafi.sh/draw/v2\n<红包编号>\n<名单哈希>\n<轮次>\n<那一轮的随机数>")`。
- **抽奖**，按这个顺序取用字节流：
  1. 从 1…N（报名人数）里用 Floyd 抽样抽 K 个序号，K = 获奖名额和报名人数里小的那个；
  2. 生成金额：份数是 K（人数不足时发完奖池）或设置的名额（不发完奖池）；
  3. 从这些金额里抽 K 个位置（Floyd 抽样），再洗牌，按序号从小到大对到中奖者。

  和现在的开奖代码步骤一样，只换了字节来源。抽人和金额在逻辑上仍是分开的两步，只是用同一个种子、按固定顺序取字节，验证一次就能重算全部。金额不能像拼手气那样在开放时就封存：发完奖池时份数要看最后有几个人报名，只能在开奖时生成。
- **取随机数**：到那一轮的时间后 0.5 秒去取（节点约 0.3 秒后才有这一轮；更早去取会拿到节点缓存住的 404，实测拖到 6 秒以后），先 Cloudflare 的节点（`drand.cloudflare.com`），取不到换 drand 官方节点（`api.drand.sh`）；都取不到就每秒再取一次，开奖推迟，🎲 页面写“正在等待随机数”。取到的要轮次对、随机数是签名的 SHA-256 才收。轮次在截止时就定死，绝不换。
- **存下**：轮次、产生时间、随机数、签名、名单哈希、种子、算法版本。写了就不能改（数据库触发器）。

## 4 拼手气和自定义金额的随机顺序（v2）

- **开放时**：服务器生成 32 字节的秘密种子 S，算出：
  - 封存值 = `SHA-256("hb.lafi.sh/queue/v2\n<红包编号>\n<S>")`，开放起就公开；
  - 队列种子 = `SHA-256("hb.lafi.sh/queue/v2/seed\n<红包编号>\n<S>")`，用来产生字节流；
  - 拼手气：用字节流生成全部金额，再洗牌，排成队列；自定义金额（随机顺序）：把发红包的人填的金额按填写顺序洗牌。

  开放时用 S 重新生成全部金额，替换草稿里预先生成的那些：草稿的金额只用于开放前的检查，从不发出（开放后本来就不能改金额）。
- **领取时**：按到达顺序拿队列里的下一份，当场出金额。现在的随机挑一份改成按顺序取（库存的位置就是队列的位置），领走的份额一直占着，付款失败也不退回给别人，所以“第 k 个领取的人拿第 k 份”始终成立。
- **结束时**（领完、到期或提前结束）公开 S。任何人都能核对：S 算出的封存值就是开放时公布的那个；用 S 重算出整个队列；名单里每人拿到的，正是他那个位置的那份；没领完的剩下几份也列出来。
- **结束前谁都看不到队列**：种子和队列不出现在任何接口里，发红包的人的管理页、统计页、管理面板都不行（现在的管理页和统计页本来就不返回库存金额）。
- **文案不能说过头**：拼手气不能说“开奖前谁都不知道”，只说“金额顺序在开放时已经封存，结束后公开，可以核对没有改过”。

## 5 界面（2026-10-22 用户看过预览后定）

所有人看到的都一样。

- **名单弹窗**：
  - 限时开奖：截止前写“截止后用 drand 第 N 轮随机数开奖”和“怎么开奖 ›”；开奖后写“用 drand 第 N 轮随机数开奖”和“开奖证明 ›”。
  - 拼手气、自定义（随机顺序）：进行中写“金额顺序已在开放时封存”和“怎么发的 ›”；结束后同样是“开奖证明 ›”。
  - 红包皮上不加东西。
- **开奖证明**（叠在名单弹窗上，下面压暗、模糊）：
  - 限时开奖：一句“中奖者和金额，由截止后的一轮 drand 公开随机数和报名名单算出。开奖前谁都不知道这个随机数。”，两行数据（随机数：第几轮、几点产生、“在 Cloudflare 上查看 ↗”；报名名单：几人，截止时冻结），一句 drand 的说明，“自己验证”。
  - 验证三步打勾：取第 N 轮随机数、读报名名单、重算中奖者和金额，最后“完全一致”。浏览器同时从两个 drand 节点取这一轮，两个节点给的都要和公布的一样，随机数要是签名的 SHA-256；不在浏览器里验 BLS 签名（用户定，2026-10-22）。
  - 有一步对不上：那一步打叉，写“对不上 / 打叉的那一步，重算的结果和公布的不一样。”；数据没取到：写“没能验证 / 没取到需要的数据，稍后再试一次。”。名单是模糊数量时，步骤里不写人数。
  - 底部“数据和算法 ›”去 🎲 页面，开奖前、发放中也有。
  - 不写算法名、随机值、名单哈希和种子，这些放在 🎲 页面。
- **🎲 页面** `/🧧/<编号>/🎲`：给较真的人看，地址栏和标签页叫“开奖数据”（限时开奖）或“发放数据”（拼手气、自定义）。能公开的随时都公开，还没到的那一步写清楚什么时候有（用户定，2026-10-22）：
  - 顶上“回到红包”；还没到最后一步时，旁边一个“刷新”，刷新后显示最新的数据。下面一句话说现在到哪一步：
    - 报名中：“还在报名。截止时冻结报名名单，再用截止后的下一轮 drand 随机数开奖。”
    - 等随机数：“名单已冻结，正在等 drand 第 N 轮随机数。”
    - 已取到随机数、还在创建付款：“已取到随机数，中奖名单已经算出，正在创建付款。”
    - 拼手气发放中：“还在发放。结束后公开种子和没领的份额，就能核对整个队列。”
  - 限时开奖：红包概要；随机数（链、轮次、时间、随机值、签名、两个节点的链接；报名中写按现在的截止时间算出的那一轮，提前截止就换成那时之后的一轮；这一轮产生以前不放节点的链接，免得有人先点出节点缓存的 404）；报名名单（报名中就列出已报名的人，可下载）和名单哈希（截止时算出）；算法逐步说明（这里写“限时开奖 v2”）和伪代码；中间结果（种子取到就公开；抽到的序号、金额、分配算出就公开）；“在浏览器里验证”逐步对照。
  - 拼手气：封存值、种子（结束后公开）；队列和领取：已经领走的份额随时公开（位置、金额、领的人、时间，名单里本来就公开），没领的写“还有 N 份，结束后公开”。
  - “复制验证脚本”：一个只用 Node 自带的库的脚本，`node verify.mjs 数据.json` 就能跑，限时开奖会从 drand 官方节点再取一次那一轮，不需要相信本站页面上的代码；“下载全部数据”存成 `开奖数据.json` / `发放数据.json`，“下载名单”存成 `报名名单.csv`。验证、复制脚本和下载全部数据在能验证以后才出现。
  - 旧红包打开写“没有开奖数据 / 这个红包用的是旧算法，或者没有随机的部分。”。自定义金额（随机顺序）的算法一节叫“随机顺序 v2”，金额一步写“发红包的人填的 N 份”。
- **公开接口** `GET /api/activities/:id/proof`：🎲 页面和验证脚本用的同一份数据，带着现在到了哪一步（限时开奖：报名中、等随机数、创建付款、已开奖；拼手气：发放中、已结束）。
- **弹窗叠层**：从红包的面板弹窗（名单、说明）里打开的弹窗，叠在它上面并压暗、模糊它（预览时发现现在不会，一并修）。

## 6 限制（照实说明）

- **拼手气的种子在服务器上**：掌控服务器的人理论上能读到种子，知道队列，等前一份被领走再去领大的；开放前也能多试几个种子挑一个。要杜绝只能领取后等 drand，用户不接受等待。缓解：每次领取的时间和顺序都公开，同一个人总能卡准大份，结束后对着数据一眼就能看出。限时开奖没有这个问题。
- **限时开奖的名单**：截止后没改，靠的是截止时就推送出去的名单哈希，加上名单本来就实时公开。截止后紧接着就出下一轮，偶尔随机数会比名单哈希的推送先到；用户定不为此多等（2026-10-22）。
- 不找第三方盖章（用户定）。

## 7 数据和实现

- `activities.random_version`：开放时定下，2 是 v2，空是旧的或没有随机的部分（固定均分、按顺序的自定义金额）；只能在开放那一刻写（触发器）。
- `activity_random_proofs`（迁移 0037）每个红包一行：
  - 限时开奖：轮次、产生时间、名单哈希、报名人数，截止时写；随机数、签名、种子、取到的时间，取到后写一次。插入时数据库核对轮次就是截止后的那一轮。
  - 拼手气：封存值和加密的种子，开放时和开放写在同一批；种子明文只在红包结束后写一次（有人第一次读 `/proof` 时）。
  - 写了不能改、不能删（触发器）；开放后的拼手气队列也不能改、不能加。
- 开奖计划的版本是 `timed_draw_v2`，多存抽到序号的先后（`picked`）给 🎲 页面。
- 限时开奖的开奖等那一轮：红包的 Durable Object 定时到那一轮的时间加 0.5 秒去取，取到就开奖；取不到每秒再来。
- 代码：算法在 `packages/contracts/src/draw-proof.ts` 和 `random.ts`（服务器和浏览器同一份）；服务器在 `apps/api/src/activities/random-proof.ts`；浏览器的验证在 `apps/web/src/lib/draw-check.ts`；验证脚本是 `apps/web/src/lib/verify-draw.mjs`，页面上的“复制验证脚本”复制的就是它。
- 测试：固定测试数据 `packages/contracts/test/fixtures/draw-proof-v2.json`（一个真实的 drand 轮次），算法、验证脚本和浏览器端到端测试都用它；接口测试用一个假的 drand 节点（`DRAND_URLS`），并把开奖用的时钟拨快，免得真等一轮；完整流程用本地的假 drand，按真实时间出轮次。
