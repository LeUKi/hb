# 三方积分：用别的网站的积分发红包（2026-11-10 定）

红包现在能从 LDC 商户或🐟额里出。这里加第三种：**三方积分**，是别的网站发行、由它自己记账的积分。PLUS 用户把自己网站的积分接进来，经过接入自检和站长审核后，大家发红包时就能选它。有人领到时，本站拿发红包的人的密钥调用对方的接口，从他在那边的账户里直接转给领取的人。本站不保管这些积分，也不预先扣下。

状态：已实现，本地和 Stage 部署完成，未推送、未上生产（2026-11-11，进度见第 14 节）。本文的规则都是用户在 2026-11-10 的几轮讨论里定的；用户没逐条点头、由我按建议定的，都列在第 15 节“待你确认”。

## 0 说法

| 说法 | 意思 |
|---|---|
| 三方积分 | 别的网站发行、自己记账的积分。不叫货币、币，也不说充值、提现（同[🐟额](balance-design.md)第 0 节） |
| 发行方 | 发行这种积分的网站，以它的接口地址的域名为准 |
| 接入人 | 在本站登记这种积分的 PLUS 用户 |
| 名称 | 这种积分叫什么，比如“星星”，出现在红包皮标签“三方｜星星”上 |
| 单位 | 写在数量后面的字，比如“300 星星”；多数时候和名称一样 |
| 最小单位 | 能转的最小数量，比如 0.01、1、100；所有数量都是它的整数倍 |
| 额度 | 一把密钥对应的账户里现在可用的积分 |
| 密钥 | 发红包的人在发行方生成、贴回本站的凭据；谁能生成、能转多少，由发行方决定 |

## 1 总则

- **谁能接入**：PLUS 用户，每人最多 3 种（建议，见第 15 节）。PLUS 到期后，已上线的照常，只是不能再接入新的。
- **一种积分的生命**：草稿 → 自检通过 → 待审核 → 上线；审核不过就退回（带理由），改了再提交。上线后站长可以暂停、恢复、下架；接入人可以自己下架。
- **钱怎么走**：领取时直接扣，同 LDC 商户直发。开放时不冻结、结束时没有要退的。
- **密钥**：发红包的人自己的。本站核验不了密钥的账户是不是他本人（LDC 也一样：凭证检查只查一笔不存在的单），所以不限制；贴密钥时显示“将从 @某人 的账户扣”。
- **不自动开户**：对方说找不到收款人，就和 LDC 一样给领取的人 5 分钟、可以重新发送一次，文案由发行方写。
- **业务失败不排队重试**：额度不够、密钥无效、不允许、参数不对、单号冲突，都当场失败；只有没拿到回复（超时、连不上、读不出）才有限地重试（第 5 节）。
- **不计入的地方**：排行榜、称号、`/me` 和红包记录里的发出与领到合计，只算 LDC 商户和🐟额。三方积分的行照常列出，写它自己的单位，不进合计。
- **一期范围**：所有玩法（固定均分、拼手气、自定义金额、限时开奖、自领、代码判定）和附带网页都能用三方积分；代码判定只能用第六版及以后的判定器（第 10 节）。社区小程序、打赏、转账不涉及：小程序不显示三方积分红包。

## 2 数量

- **口径只有一个，以本站为准**：接口里的数量一律是“整数分”的十进制字符串，范围 1 到 9,007,199,254,740,991（最大安全整数）。1 个积分就是 "100"；最小单位是 1 的积分，数量永远是 100 的倍数。对方底层怎么存、怎么换算，是对方的事。
- **最小单位**：0.01 的任意倍数，最大 1 亿。所有数量（总额、每份、额度检查）都必须是它的整数倍。
  - LDC 和🐟的最小单位是 0.01，也就是 1 分，所以“整数分”和“多少个最小单位”在它们身上是同一件事，现有的一切不变。
  - 拆分（拼手气、限时开奖抽奖、随机顺序）先换算成“多少个最小单位”，用现有算法拆，再乘回去；LDC 照旧。
  - 平分：总数要能被“份数 × 最小单位”整除；每份至少一个最小单位。
  - 上线后可以改成更细的单位（新单位能整除旧单位，比如 100 改 10）；改粗要等没有开放中的红包。改最小单位都要重新自检和审核。
- **显示**：
  - 小数位跟着最小单位：整数不带小数，0.5 带一位，0.25 带两位。LDC 和🐟照旧两位。
  - 长数字缩写成万、亿、万亿：不到 100 万照写（带千位分隔）；100 万到 1 亿写“123.4 万”；1 亿到 1 万亿写“1.2 亿”；再往上写“12.3 万亿”。上限约 90 万亿，用不到科学计数法。
  - 缩写保留一位小数，直接截掉、不四舍五入（显示的数不会比实际多，99,999,999 写“9,999.9 万”），末尾 .0 省掉。
  - 完整的数放在气泡提示里，也给读屏。输入框照写完整的数，旁边小字写读法（“= 1.2 亿 星星”）。
  - 三种出资用同一个金额组件。

## 3 发行方的接口（协议第一版）

发行方提供一个接口地址（`https://` 开头，比如 `https://stars.example.com/hb`），在它下面实现三个接口。

**共同的规则**：

- 都是 `POST`，请求体和回复都是 JSON（UTF-8）。
- 请求头：`Authorization: Bearer <密钥>`、`Content-Type: application/json`、`Hb-Points-Protocol: 1`。
- 以回复 JSON 里的 `result` 为准，HTTP 状态码不看。读不出 `result`、超过 10 秒、回复超过 64 KB、跳转（3xx），都算“没拿到回复”。
- 人一律按 LINUX DO 数字 ID 认；用户名只用来显示和记录。
- 本站的单号 `out_trade_no`：不超过 64 个字符，只有字母、数字、`_`、`-`。

**额度** `POST {接口地址}/balance`，请求体 `{}`：

```json
{ "result": "ok", "account": { "id": 12345, "username": "alice" }, "available": "123400" }
```

`available` 超过上限按上限算。密钥不对回 `{ "result": "key_invalid" }`。

**发放** `POST {接口地址}/transfer`：

```json
{ "out_trade_no": "hbp_01J…", "to": { "id": 67890, "username": "bob" }, "amount": "10000", "remark": "红包站 · 新年快乐" }
```

| `result` | 意思 | 要求 |
|---|---|---|
| `ok` | 转好了，带上 `trade_no`（对方的单号）、`amount`、`to.id` | 同一个 `out_trade_no` 再来，回同一笔，不重复转 |
| `insufficient` | 额度不够 | 没有建单 |
| `no_recipient` | 找不到收款人（他在那边没有账户） | 没有建单 |
| `not_allowed` | 不允许（发行方自己的规则，比如这个人被限制） | 没有建单 |
| `key_invalid` | 密钥无效或被收回 | 没有建单 |
| `bad_request` | 参数不对（比如不是最小单位的倍数） | 没有建单 |
| `conflict` | 这个单号用过，但收款人或数量不一样 | 没有建单、不转 |

除 `ok` 以外的回复都保证没有建单，这是本站能“当场失败”的前提。

**查单** `POST {接口地址}/query`，请求体 `{ "out_trade_no": "…" }`：成功回 `{ "result": "ok", "trade_no", "amount", "to": { "id" } }`；没有这笔回 `{ "result": "not_found" }`；密钥不对回 `key_invalid`。

`remark` 是“红包站 · 红包标题”，最多 60 个字。

## 4 接入自检

接入人在配置页填好接口地址、一把测试密钥（加密保存，只用于自检）和一个测试收款人的 LINUX DO ID（可以是自己，前提是对方允许自己转给自己），本站按顺序跑下面这些步骤。每一步记下发了什么、回了什么、用了多久，密钥打码。一共真实花掉 1 个最小单位。

| # | 本站做什么 | 必须得到 | 证明什么 |
|---|---|---|---|
| 1 | 用一把错的密钥查额度 | `key_invalid` | 真的在验密钥 |
| 2 | 用测试密钥查额度 | 账户 ID、用户名、可用（格式对） | 密钥和账户对得上 |
| 3 | 查一个从没发过的单号 | `not_found` | 本站靠它区分“没发出”和“不知道发没发出” |
| 4 | 给测试收款人发 1 个最小单位 | `ok`，带对方单号 | 真的能转 |
| 5 | 查这一笔 | `ok`，数量、收款人、单号都一致 | 查单可靠 |
| 6 | 同一个单号原样再发 | `ok`，同一个对方单号 | 不会重复转（最要紧的一条） |
| 7 | 再查额度 | 正好少了 1 个最小单位 | 再核一遍第 6 步 |
| 8 | 同一个单号换个数量再发 | `conflict` | 单号不能被挪用 |
| 9 | 发给一个随机生成、不可能存在的 ID，再查这一笔 | 先 `no_recipient`，再 `not_found` | 找不到收款人能走通，而且没建单 |
| 10 | 发 9,007,199,254,740,991 分，再查这一笔 | 先 `insufficient` 或 `bad_request`，再 `not_found` | 接得住本站的上限，额度不够也没建单 |
| 11 | 最小单位大于 0.01 时：发“最小单位加 0.01” | `bad_request` | 最小单位的规则在对方那边也成立 |

- 每一步都检查：HTTPS、不跳转、10 秒内、回复不超过 64 KB、JSON 格式对。
- 两次自检之间至少隔 30 秒（同 LDC 凭证检查）。测试账户在自检期间不要有别的进出，否则第 7 步会对不上。
- 改接口地址或最小单位，要重新自检、重新审核；只改文案不用。
- 全部通过才能提交审核；提交时带上这次自检的记录。

## 5 发放和失败

| 发放的回复 | 本站怎么做 |
|---|---|
| `ok` | 已发放 |
| `insufficient`、`key_invalid` | 这一份未发出；**红包立刻结束**，提醒发红包的人（文案由发行方写）。同一个红包遇到一次以后，后面的发放（包括代码判定红包结束时的集体结算、正在领的）不再调用对方，直接记未发出 |
| `no_recipient` | 给领取的人 5 分钟倒计时、可以重新发送一次，过时未发出；红包照常 |
| `not_allowed` | 这一份未发出，显示发行方写的文案；红包照常 |
| `bad_request`、`conflict` | 这一份未发出，进站长后台的“异常”：说明对方的实现有问题 |
| 没拿到回复 | 先查单：查到 `ok` 就算已发放；查到 `not_found` 就用原单号重发。最多重发 3 次（1、5、30 分钟后）。3 次以后查单确认没有这笔，就算未发出；查单也不通，就标“结果不明”，停下等站长 |

- “不知道发没发出”的单绝不直接算失败。
- **熔断**：同一种积分连续 5 次没拿到回复，暂停它的发放 10 分钟，后台能看到。暂停期间，新来领的在占份额之前就挡住（“星星暂时发不出，稍后再来”），不留未发出记录。站长暂停时同样挡。
- **开放时检查额度**：额度不少于这个红包的总额，加上同一把密钥下其他开放中红包还没发出的部分。不够就不能开放，说清差多少。
- **兑现前再查一次**：限时开奖开奖前、定时开放到点时，再查一次额度；不够就不开奖（红包结束）或不开放，提醒发红包的人。免得有人被告知中奖却收不到。
- **没有要退的**：直接扣，没发出去的本来就还在发红包的人那边。

## 6 发行方的配置页

每一项都写清楚“出现在哪、什么时候、谁看到”，旁边用本站的真组件直接预览。

| 配置 | 限制 | 出现在哪 | 预览 |
|---|---|---|---|
| 名称 | 1–6 个字 | 红包皮标签“三方｜名称”、详情页 | 真红包皮 |
| 单位 | 1–4 个字 | 数量后面 | 金额三格、长数字的例子 |
| 最小单位 | 增减组件 | 拆分、输入、显示 | 旁边写出它意味着什么（“每份至少 100 星星，只能是 100 的倍数，显示不带小数；自检会花掉 100”） |
| 发行方名称 | 1–20 个字 | 详情页 | 详情页 |
| 介绍 | md，最多 2000 字 | 详情页 | 详情页 |
| 填密钥的引导 | md，最多 2000 字 | 发红包时选了这种积分、还没填密钥时的叠层弹窗 | 弹窗本身 |
| 找不到收款人 | md，最多 1000 字 | 领取的人的结果卡（带倒计时和“重新发送”），详情页“怎么领到” | 结果卡，倒计时真的在走 |
| 到账说明 | 最多 60 字 | 领到以后的结果卡 | 结果卡 |
| 不允许 | 最多 60 字 | 领取的人的结果卡 | 结果卡 |
| 额度不够 | 最多 100 字 | 发红包的人看到的提醒 | 提醒 |
| 密钥失效 | 最多 100 字 | 发红包的人看到的提醒 | 提醒 |

- **增减组件**：可以直接输入 0.01 的任意倍数（最大 1 亿）；减、加按钮按 1、2、5 走（…0.5、1、2、5、10、20、50、100…），输了 25 按加号到 50、按减号到 20。
- **仿真**：选一个身份（发红包的人、领取的人），从填密钥、开放、有人来领，一直走到每一种回复，全在页面里，不发任何请求。真接口就是自检。
- **md**：用本站说明的同一个渲染器，不显示图片（外链图片能看到谁打开了页面）；链接不限制，新标签页打开。
- **改文案**：立即生效，留改动记录（改前改后）；站长后台没看过的改动标红点。

## 7 站长审核和后台

- **审核**：看配置、详情页预览和自检记录，通过或退回（写理由）。
- **每种积分一行**：状态（草稿、待审核、上线、暂停、熔断中、下架）、今天三种接口各调了多少次、成功率、平均耗时、连续没拿到回复的次数、开放中的红包数。
- **待处理**：“结果不明”的单（可以再查一次，或标为未发出）；`bad_request`、`conflict` 的单。
- **最近的失败**：按原因分开。
- **改动记录**：改前改后对比，没看过的标红点，看过就消。
- **自检记录**。
- **操作**：暂停、恢复、下架。下架时开放中的红包立即结束。
- 页面不自动刷新，用刷新按钮。

## 8 发红包的人

- **从哪发**：表单“从哪发”加第三项“三方积分”（总开关开着、至少一种已上线时才有），选了再选哪一种。
- **密钥**：每种积分存一把（加密）。还没有就弹出叠层弹窗：发行方写的引导、一个密钥输入框；贴上以后马上查一次额度，显示“可用 1,234 星星，将从 @alice 的账户扣”。可以换、可以删；删掉后，用这把密钥的开放中红包结束。
- **金额输入**：按这种积分的单位和最小单位，提示“每份至少 1 星星，只能是 1 的倍数”。
- **开放**：照第 5 节检查额度。
- **提醒**：红包因为额度不够、密钥失效、删了密钥或下架而提前结束时，发红包的人在自己的红包页顶上看到一条说明（有发行方的文案就用它）；定时开放到点额度不够，照定时开放的规则退回草稿、写明原因；限时开奖开奖前额度不够，不开奖，红包结束。

## 9 领取的人

- **标签和气泡**：“三方｜星星”；气泡写“来自 **stars.example.com** 的积分，领到后存进你在这个网站的账户。”，下面“查看详情 ›”。鼠标点标签直接打开详情页；触屏点一下出气泡，气泡里有按钮；键盘聚焦出气泡，回车打开。
- **详情页** `/points/:id`：顶部标签、发行方名称、域名（点开到对方网站）、状态；“三方积分是什么”（本站固定文案）；发行方的介绍；怎么领到（找不到收款人那段 md）；基本信息（最小单位、接入人、上线时间）。固定文案：

  > 三方积分是其他网站的积分，红包站不保管。发红包的人从他在那个网站的账户里出，领到的直接进你在那个网站的账户。积分能做什么、值多少，由那个网站决定，红包站不核对，也不兑换。

- **隐私**：领取按钮下方一行“领取时会把你的 LINUX DO 用户名发给 stars.example.com。”
- **结果卡**：已发放写“已存进你在 stars.example.com 的账户”加发行方的到账说明；找不到收款人显示发行方的 md、倒计时和“重新发送”；不允许显示发行方的文案；其他未发出照现在的写法。

## 10 代码判定和附带网页

- **判定器要声明 `meta.points: true` 才能用在三方积分红包上**。用户 2026-11-10 定的是“第六版及以后的判定器才能用，第五版及以前的只能用在 LDC 和🐟红包”；实现时改成了声明（第 15 节第 7 条）：协议号放宽到 6 要重建 `activity_code`、`judge_versions`、`judge_usage` 三张表和它们的全部触发器，风险大，而“现有判定器都不能用、作者主动改了才能用”这一点，声明一样做到。
- **声明了的判定器，金额都是整数，表示多少个最小单位**。LDC 和🐟的最小单位是 0.01，就是分，所以对它们什么都不变。
  - 本站存数照旧用分，交给判定器时除以最小单位，收回 `add`（自己的和 `others` 的）时乘回去；所有数都是最小单位的整数倍，两头都除得尽。`check()`、`setup()` 拿到的 `hongbao` 也一样换算。
  - 判定器多拿到 `hongbao.unit`（"LDC"、"🐟" 或积分单位）、`hongbao.step`（"0.01"、"1"…）、`hongbao.points`（名称、单位、域名，别的红包是 null）。
  - `tools.money.format()` 按 `hongbao.step` 定小数位：LDC 2000 → "20.00"，最小单位 1 时 2000 → "2000"。
  - `hongbao.count`（`even()` 缺省的 n）按“100 个最小单位”取整，公式不变。
  - 判定器的金额参数：发红包的人按积分的单位填，存的是多少个最小单位；红包页按单位显示。
  - 自己的服务签的凭证，金额也是多少个最小单位。
- **附带网页 SDK 和红包信息接口**：照旧 v1，只做向后兼容的扩展：`unit` 放宽成字符串；新增 `step`、`points`；金额字符串按最小单位定小数位（精确值，不缩写）；红包信息接口另给 `units: { pool, unclaimed }`（多少个最小单位）。写死 “LDC” 的旧网页放到三方积分红包上，单位会显示错；网页不管钱，发红包的人选网页时看得到预览。

## 11 安全

- 接口地址只许公网 `https://`，不许 IP 地址、`localhost`、本站自己的域名（`lafi.sh` 及其子域）。
- 不跟随跳转；回复限 64 KB、10 秒。
- 对方回来的用户名等一律当纯文本显示。
- 密钥和测试密钥加密保存（同 LDC 凭证），日志和自检记录里打码。
- 名称和单位不能是 LDC、🐟、Credit、红包站、🐟额这类词，也不能和已有的重复。

## 12 开销

- 调用对方接口放在每把密钥一个的队列对象里（同 LDC 每个商户一个），不进红包自己的对象：等对方回复时对象一直醒着，慢的发行方不该拖住红包。
- 业务失败不重试、没拿到回复最多 3 次、熔断，三条一起保证一个坏掉的发行方不会无限消耗。
- 发行方可以设每秒最多被调用几次（默认 10）。

## 13 实现

- **共用的数量规则**（`packages/contracts/src/amount.ts`、`points.ts`）：`formatUnitAmount`（精确、按最小单位定小数位，接口和 SDK 用）、`formatDisplayAmount`（千位分隔、万亿缩写，界面用）、`parseUnitAmount`、`moneyStepIssue`（按最小单位查红包的金额，服务端和表单共用）、1-2-5 增减序列。`generateRandomAmounts`、`drawAmounts`、`drawPlanV2`、`queueAmountsV2` 加 `step` 参数，缺省 1：LDC 和🐟抽出来的一个字节都不变。
- **数据库**（迁移 0062）：
  - `points_systems`（配置、状态、自检、审核、熔断）、`points_copy_changes`（文案改动，站长看过记 `seen_at`）、`points_self_tests`（每一步的记录，密钥打码）、`points_keys`（发红包的人的密钥，加密，每人每种一把）、`points_payments`（每一笔发放）、`points_calls`（每一次调用，后台统计用，保留 30 天）、`points_settings`（总开关，带版本）。
  - `activities` 加 `points_system_id`；`funding` 加 `points`。`funding` 由触发器检查，换掉 `activities_funding_insert_valid` 和 `_update_valid` 两个触发器即可，不重建大表。三方积分红包 `payment_mode` 记 `real`，`merchant_id` 为空。
- **不走 LDC 的付款流水**：LDC 的 `payment_tasks` 有“同一单号查过才能重发、无限等待”一整套触发器和恢复规则，和“业务失败当场结束、网络问题最多 3 次”正好相反。三方积分用自己的 `points_payments`，规则简单，也不会碰坏 LDC 的付款。
- **怎么调用对方**：领取的同一批写入里插一行 `points_payments`，写完由队列（`PAYMENT_QUEUE`，消息 `points.run`）去发；重试用队列的延迟投递（1、5、30 分钟），每 5 分钟的维护任务再兜底扫一遍到期的。都不在红包自己的对象里等对方回复。同一笔用租约防止同时发两次。
- **结果怎么给页面**：领取详情、名单照旧拿 `PaymentView`（状态 pending、sending、confirmed、attention、failed 等），从 `points_payments` 换算出来，网页现有的“发放中、已到账、未发出、重新发送”都能直接用；三方积分专有的文案（找不到收款人、不允许、到账说明）另带在红包的三方积分信息里。
- **页面**：`/points`（我接入的三方积分）、`/points/:id/edit`（配置页、预览、仿真、自检、提交）、`/points/:id`（详情页，登录的人还能在这里管自己的密钥）、`/admin/points`（审核和后台）。
- **网页显示**：一个金额组件 `UnitAmount`、一个 `unitOf(红包)`；现有约 120 处写死的 “LDC” 逐处换掉（只换显示红包金额的地方，🐟额、Credit、商户、打赏这些本来就是 LDC 的不动）。
- **判定器**（第 10 节）：现行运行时（协议第五版，没有冻结）的 `readMeta` 收 `points: true`，`tools.money.format()` 按 `hongbao.step` 写；`apps/api/src/points/judge.ts` 在判定边界换算（`submissionForJudge`、`readingFromJudge`、`hongbaoForJudge`），`judge/batch.ts`、`params.ts`（check）、`opening.ts`（setup）调用；开放三方积分的代码判定红包要求判定器声明了 `meta.points`（`JUDGE_NOT_FOR_POINTS`）。不加迁移。
- **示例发行方** `examples/points-issuer`：协议第一版的最小实现（一个 Durable Object 的 SQLite 账本、开户和发密钥的演示页），Stage 上部署为 `https://hb-points-demo.lafish.workers.dev`（接口地址 `…/hb`）；本地完整应用用 `HB_FULL_APP_POINTS_ISSUER=http://127.0.0.1:8790` 把 `https://stars.points.test` 转给它。
