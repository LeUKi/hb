# 代码判定红包（2026-10-24 定，代码协议待细化）

用户提出（2026-10-24）：让会写代码的人自己决定红包怎么发，比如输入不同的内容领不同的金额、每个人的口令不一样、口令按用户名和时间生成。现有的玩法做不到，做成一种新玩法：发红包的人写一段代码，每次有人提交，由代码判定领不领得到、领多少。代码在 Cloudflare Dynamic Workers 的沙箱里跑。

## 0 说法

| 说法 | 意思 |
|---|---|
| 代码判定红包 | 这种新玩法，简称“代码判定”，同“拼手气红包 / 拼手气”（用户定，2026-10-24；先叫过“可编程”，单独放着像缺了后半句） |
| 代码 | 发红包的人交的一个 JavaScript 文件，开放后不能改 |
| 提交 | 领的人在指令框里输入后按“领取” |
| 判定 | 代码对一次提交的回答：发多少，或者不发 |
| 每份至少 | 保底，每份最少发多少（第 2 节） |
| 指纹 | 开放时代码的 SHA-256 |
| 沙箱 | 跑代码的 Dynamic Worker |
| 开发包 | 发红包的人在自己电脑上写代码、跑测试的工具（第 5 节） |

## 1 谁能发、怎么发

- 只有开通🐟额 PLUS 的人能发，只能从🐟额发：开放时锁定整个奖池（用户定）。PLUS 能邀请别人、开了不收回（[🐟额设计](balance-design.md)第 13 节），所以真出问题时靠下面的开关和停用。
- 每人每天最多开放 3 个，站长在网站设置里能改。
- 网站设置里单独一个“代码判定红包”开关，默认关。关着时不能新建、不能开放；已经开放的照常领、照常退回。
- 站长能停用某一个代码判定红包：停止领取，剩下的退回发红包的人的🐟额，留下记录。别的红包没有这个功能。
- 发红包还是四步：玩法 → 发多少 → 代码 → 起个标题。
  - 第 1 步“更多玩法”里多一张“代码判定”卡，带 PLUS 标记。没开通的人看不到这张卡，也不放灰的。
  - 第 2 步填总奖池、份数和每份至少；“从哪发”锁在🐟额。
  - 第 3 步“代码”取代“怎么领”（第 5 节）。

## 2 钱

- 总奖池、份数、每份至少开放后都不能改。每份至少默认 0.01，不能低于 0.01（用户定）；总奖池 ≥ 份数 × 每份至少。
- 每次领到发多少由代码定。每一份有一个能发的范围，代码返回的数先四舍五入到 0.01，再拉进这个范围：

| | 最少 | 最多 |
|---|---|---|
| 不是最后一份 | 每份至少 | 剩余奖池 −（剩余份数 − 1）× 每份至少 |
| 最后一份 | 剩余奖池 | 剩余奖池 |

- 最后一份发完剩下的全部，不管代码返回多少（用户定），所以领完不会有剩。到截止时还有份没人领，剩下的退回🐟额。
- 例子：总奖池 100、10 份、每份至少 0.01，代码每次返回 1：前 9 份各 1，第 10 份发 91。代码给得少，最后一份就大，可能有人故意等到最后才领；不想这样，代码自己把钱摊开。开发包的模拟会列出每一份发多少。
- 被拉进范围时（多了封顶，少了保底，或者是最后一份），代码给的数和实际发的数都记下。领的人在自己的结果里看到“按上限发”“按每份至少发”或“最后一份，发完剩下的”；发红包的人在记录里看得到两个数。
- 名单照旧公开昵称、时间和金额。

## 3 领取

- **在哪领**：只在红包页。点「开」展开指令框，作用域标签是黑金的“代码判定 · 标题”，输入用等宽字。必须输入，没有直接领。首页不匹配（做不到：要跑每个红包的代码），所以和关闭首页领取的红包一样，强制加入红包广场。分享文案同关闭首页领取：写红包页地址和发红包的人的提示。
- **输入**：单行，1–200 个字。首尾空白去掉，其余原样：区分大小写，空格和符号都算，没有口令框的“优化”。框上方是发红包的人写的提示（最多 40 个字），下方固定写“原样提交：区分大小写，符号都算，首尾空格会去掉”。输入照旧不进地址栏、浏览历史和浏览器存储。
- **顺序**：登录、不是自己发的、领取范围、尝试间隔（活动页默认 2 秒）、人机验证（打开时）都照旧先查，不过的不调用代码；过了再交给代码判定，按判定发钱。
- **人机验证**：发红包的人打开“领取前人机验证”时，每次提交都要先通过验证，再交给代码判定（用户定）。口令红包是口令对了才弹验证；这里要跑了代码才知道对不对，所以没法只在“会受理”时才弹。
- **回复**：代码拒绝时回一句话；领到时也可以回一句话。都是纯文字，最多 100 个字，标明“代码的回复”。
- **试几次**：平台不限次数，也不替代码拦人（用户定：“每人最多提交几次”的设置和“不能再试”的标记都不要，增加复杂度，心智负担也大）。要限次数，代码按传进去的“被判定过几次”自己拒绝，在回复里写清楚。
- **出错和超时**：代码出错或超时，这次不算领取，也不算被判定过一次，提示“红包的代码出错了，请稍后再试”。连续 5 次就自动暂停领取，并通知发红包的人；暂停以后，发红包的人可以提前结束，剩下的退回。除此以外，提前结束的规则照旧（有人领过就不能）。
- **排队**：同一个红包的提交在它的 Durable Object 里排队，一次只判定一个。剩余奖池、已领记录、代码的状态都由平台传进去，代码不靠全局变量记东西。每个红包每秒最多受理 20 次提交（暂定），超出的请对方稍后再试，不调用代码。
- **尝试统计**：照旧记下每次的输入，只给发红包的人看。

## 4 代码（协议草案，下一步细化）

- 一个 JavaScript 文件（ES 模块），最大 64 KB。导出判定函数 `judge` 和测试 `tests`（用户定：不叫 `claim`，那是领的人在做的事，代码做的是判定）。
- **传进去的**：
  - 红包：标题、总奖池、总份数、每份至少、剩余奖池、剩余份数、这一份的范围（最少、最多、是不是最后一份）、开放时间、截止时间。
  - 已领记录：每份的金额、领的人（数字 ID、用户名）、时间、当时的输入。
  - 领的人：数字 ID、用户名、等级、在这个红包里被判定过几次。
  - 这一次：输入、时间、随机数。
  - 状态：上次有人领到时代码存下的。
- **交给代码的，等于交给发红包的人**：代码能把收到的东西写进状态或回复。所以只传领的人愿意让发红包的人知道的：名单上本来就有的（数字 ID、用户名），和他自己输入的。等级要不要传，细化协议时再定。
- **返回的**：发多少（数字，单位🐟）、可选的一句话、可选的新状态；或者拒绝的一句话。
- **状态**只在有人领到时保存，最大 16 KB。所以重放只需要领到的那些记录。
- **随机数**由封存的种子、领的人和他第几次被判定算出，别人的提交影响不到。种子开放时封存、结束后公开，取法同[开奖证明](draw-proof-design.md)第 2 节。
- **能用的能力**由本站定，第一版列一个清单：JavaScript 内置对象、摘要和 HMAC、文本编解码、本站的辅助函数。其余全局对象在代码运行前删掉。`Date` 和 `Math.random` 换成平台给的时间和随机数。第一版不联网，没有 `fetch`。
- **限制**：每次调用 CPU 50 毫秒（线上实测约 2 秒才会被杀，第 7 节），平台最多等 300 毫秒，到点按超时算。
- **待细化**：字段名和类型、金额用数字还是字符串、测试的写法、辅助函数清单、错误怎么分类。

## 5 开发和检查

- **第一版只做本地开发包**（用户定），不做浏览器里的运行环境。开发包放在主仓库，用 MIT 许可（主仓库是 AGPL，作者照模板写的代码不受牵连），和协议一起发版。它用 wrangler 的本地运行时，和线上同一个引擎；外层和线上同一层包装（同样的能力清单、传入的数据和结果校验）。本地不限 CPU，开发包按时间掐断。
  - `npm test`：跑代码里的 `tests`。
  - `npm run check`：和网站的在线检查同一套规则。
  - `npm run simulate`：一批虚拟的人来领，列出每份发多少。
  - `npm run replay`：发红包的人用下载的完整记录重放核对。
- **给 AI 的材料**：大多数作者会用 AI 写代码（用户判断）。开发包里放 `AGENTS.md`（协议、限制、能力、例子、常见错误）、Claude Code 的 skill 和 Cursor 的规则；网站上的“给 AI 的说明”是一段能整段复制给聊天 AI 的提示词。不做 MCP 之类的接口，最后一步总是在网站上粘贴代码（用户定）。
- **网站上**只有粘贴框和“在线检查”：在和线上一样的沙箱里跑一遍平台的检查（能加载、导出对、测试全过、耗时）。每人每天 10 次。开放前必须通过，检查的就是要开放的那份代码。

## 6 透明和核对

- 开放时公布代码的指纹和随机种子的封存值。总奖池、份数、每份至少本来就在红包页上，开放后不能改。
- 结束后对所有人公开代码和随机种子，谁都能核对代码没换过。名单照旧（昵称、时间、金额），每份写明有没有被拉进范围。哈希写法同开奖证明（SHA-256、各项换行分隔），方便手算。
- 不公开任何人的输入，也不公开代码存的状态，因为状态里可能记着输入（2026-10-24 用户指出领取记录会带上别人的输入，改成这样）。口令红包结束后虽然公开全部口令，但谁用了哪个，只有本人和发红包的人看得到；代码判定红包还可能让人输入任何东西。代价是别人没法独立重放全部领取，公开核对只到“代码没换过、钱的账对得上”。
- 发红包的人能下载完整的领取记录（每份领到时交给代码的数据，含输入和状态），用开发包重放。这和现在一样：口令红包的名单弹窗里，发红包的人本来就看得到每个人用的口令。
- 领的人在自己的结果里看得到自己交的输入和代码的回复。

## 7 运行：Dynamic Workers

- 每份代码一个独立的 isolate：不给任何绑定和密钥，网络断开（`globalOutbound: null`）。
- isolate 的 ID 用代码的指纹：同一份代码一天里调用多少次都只算一个，几个红包用同一份代码也只算一个。
- 超时以后，下一次换一个新的 isolate，免得排在卡住的那个后面。
- **费用**（官方价格，2026-06）：按“代码 × 天”计，每月 1,000 个免费，之后每个 0.002 美元；请求和 CPU 按 Workers 原价，算在现有套餐里。正式的红包每开一天算一个，测试都在本地，在线检查限次数，所以几乎不花钱。
- **实验**（2026-10-24，单独的实验 Worker `hongbao-code-lab`，不碰线上服务；用户同意留着以后再测）：
  - 第一次加载 15–20 毫秒，之后不到 1 毫秒到几毫秒；在 Durable Object 里连续判定 12 次，第一次 18 毫秒，之后每次不到 1 毫秒，状态靠参数一路传对。
  - 断网有效，`eval` 被禁，环境变量是空的。
  - 吃爆内存只死沙箱自己，下一次照常。
  - CPU 上限要到“设的值 + 约 2 秒”才杀（设 10、50、200 毫秒都是约 2.2 秒），所以平台要在外面自己计时；死循环时调用方不受影响，但后面对同一份代码的调用会排在它后面。
  - 运行中 `Date.now()` 不走；本地会走，本地也不限 CPU。
  - 语法错在加载时就报出来，在线检查能查到。
  - 出网网关（第二版要用）：只放行声明的网站，11 毫秒；别的网站被拒。

## 8 界面

草稿 2026-10-24 给用户看过，文字还要定。

- **颜色：黑漆描金**（用户定，2026-10-24）。
  - 红包皮是暖一点的黑（三段渐变，左上一点暖光），斜着一道很淡的光泽，满铺一层很淡的金色回纹；边是有明暗的金属金。
  - 标题是金色渐变字，标签、数字、进度条都偏金；印章照旧是金的，上面的字是深色。
  - 先试过近乎纯黑，用户觉得像失败、过期的红包，所以要靠金色和光泽撑住“还在进行”。
  - 结束后变冷灰，不沿用红包的“去饱和再压暗”：黑色压暗还是黑，分不出进行中和已结束。
- **标签**：红包皮上一个金色描边的“代码判定”；广场卡片上一个黑底金字的“代码判定”。
- **代码一节**：在红包页上，口令红包这个位置是口令区。进行中写指纹（可复制）和能拿到什么（第一版“不联网，代码只拿得到你的输入、用户名和等级”）。结束后展开代码全文，指纹旁写“和开放时一致”。完整的领取记录只在发红包的人自己的页面上下载。
- **第 3 步“代码”**：领取时的提示（n / 40）、粘贴代码（文件名和大小）、在线检查（今天还能检查几次，结果逐条打勾，指纹），下面是开发文档、给 AI 的说明、本地开发包三个入口，最后一句“开放后代码不能改；结束后所有人都能看到代码。”

## 9 第二版：联网

- 开放前声明要连的网站：最多 3 个，只许 https 和完整域名，不许通配符和 IP，不许 linux.do 和本站。开放后不能改。公开在红包皮的标签（“联网 · 域名”）和代码一节上，写明领取时会把什么发过去。
- 所有请求经平台的网关：只放行声明的网站，每次判定最多几次请求，3 秒超时，用红包的密钥给请求签名，对方能确认是本站发的。
- 结果依赖对方的回答，不能完全重放，页面写明。
- 这也是“让对方的服务器或 Worker 承担运算”的做法：代码把提交转给自己的接口（用户提出）。

## 10 不做

- “每人最多提交几次”的设置和代码宣布“不能再试”的标记（用户定）。
- 浏览器里的运行环境（第一版）；QuickJS（用户定）；MCP 之类的创建接口（用户定）。
- 商户直发、限时开奖式的代码判定：只做从🐟额发、即时判定。
- 分档：份额不预先分好，金额由代码定（用户定：分档能做的场景太少）。

## 附录：调研（2026-10-24）

**别家的做法**

| 产品 | 做法 | 借鉴 |
|---|---|---|
| 支付宝口令红包 | 一个口令大家领；会员活动用各自的手机号当个人口令；分时段换口令；连错有冷却 | 2024 年有人猜中“祝爸妈新年快乐”领走一万元：人想的口令，难猜比长度要紧 |
| QQ 红包 | 口令、问答（答错无限重试）、接龙、画图；专属红包指定给某个人 | 玩法多样，规则由平台写死 |
| 币安红包 | 平台生成口令；每人一次；连错 10 次锁 5 小时 | 公开的口令几分钟内就被聚合网站收走 |
| CTF 平台（CTFd、GZCTF） | 一题多个答案、每队的 flag 由哈希算出、前三名加分、可限尝试次数 | 每人不同的答案挡得住抄答案，挡不住分享解法；CTFd 的分数会回溯下调，钱发出去做不到 |
| Shopify Functions | 商家的代码编译成 WebAssembly，限 1,100 万条指令 | 平台给数据、代码只返回决定，和这里的做法一样 |

**技术比较**

| 做法 | 结论 | 理由 |
|---|---|---|
| Dynamic Workers | 选它 | 每份代码独立的 isolate，能限 CPU、能断网、能经网关联网；按“代码 × 天”计费，几乎不花钱；2026-03 起公测 |
| QuickJS（WebAssembly） | 不做（用户定） | 跑在本站自己的进程里，内存上限有已知漏洞，只能数步数限时，一个人业余维护，没审计 |
| 直接调发红包的人的接口 | 归到 Dynamic Workers 里（第二版联网） | 单独做的话逻辑在对方服务器，没法公开核对 |
| CEL 之类的表达式语言 | 不需要 | 安全，但表达力不够；这里要的是任意逻辑 |
| Workers for Platforms、Containers | 不合适 | 前者每月多 25 美元、每改一次要部署；后者冷启动 0.6–3 秒 |
| `eval`、`new Function` | 不能用 | Workers 禁止在运行时生成代码 |
