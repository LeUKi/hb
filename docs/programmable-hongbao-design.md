# 代码判定红包（2026-10-24 定）

用户提出（2026-10-24）：让会写代码的人自己决定红包怎么发，比如输入不同的内容领不同的金额、每个人的口令不一样、口令按用户名和时间生成。现有的玩法做不到，做成一种新玩法：红包作者写一段代码，每次有人提交，由代码判定领不领得到、领多少。代码在 Cloudflare Dynamic Workers 的沙箱里跑。

## 0 说法

| 说法 | 意思 |
|---|---|
| 代码判定红包 | 这种新玩法，简称“代码判定”，同“拼手气红包 / 拼手气”（用户定，2026-10-24；先叫过“可编程”，单独放着像缺了后半句） |
| 代码 | 红包作者交的 `judge.js`，开放后不能改，结束后公开 |
| 测试 | 红包作者交的 `tests.json`，只是数据，不算进代码，不公开 |
| 提交 | 领的人在指令框里输入后按“领取” |
| 判定 | 代码对一次提交的回答：发多少，或者不发 |
| 每份至少 | 保底，每份最少发多少（第 2 节） |
| 指纹 | 开放时 `judge.js` 的 SHA-256 |
| 种子 | 本站开放时生成的秘密随机数：开放时公布封存值，结束后公开（第 4.4 节） |
| 分 | 金额的单位，0.01；代码里的金额都是整数分 |
| 沙箱 | 跑代码的 Dynamic Worker |
| 开发包 | 红包作者在自己电脑上写代码、跑测试的工具（第 5 节） |

## 1 谁能发、怎么发

- 只有开通🐟额 PLUS 的人能发，只能从🐟额发：开放时锁定整个奖池（用户定）。PLUS 能邀请别人、开了不收回（[🐟额设计](balance-design.md)第 13 节），所以真出问题时靠下面的开关和停用。
- 每人每天最多开放 3 个，站长能改。
- 单独一个“代码判定红包”开关，默认关。关着时不能新建、不能开放；已经开放的照常领、照常退回。
- 这几项、部署次数和每月判定器上限都在网站管理的“判定器”页签，用量也在那里看（第 7 节，[07](redesign/07-pages.md) 第 10 节）。
- 站长能停用某一个代码判定红包（网站管理红包页签的详情里，[07](redesign/07-pages.md) 第 10 节）：停止领取，剩下的退回红包作者的🐟额，留下记录。别的红包没有这个功能。
- 发红包还是四步：玩法 → 发多少 → 代码 → 起个标题。
  - 第 1 步“更多玩法”里多一张“代码判定”卡，带 PLUS 标记。没开通的人看不到这张卡，也不放灰的。
  - 第 2 步填总奖池、份数和每份至少；“从哪发”锁在🐟额。
  - 第 3 步“代码”取代“怎么领”（第 5 节）。

## 2 钱

- 总奖池、份数、每份至少开放后都不能改。每份至少默认 0.01，不能低于 0.01（用户定）；总奖池 ≥ 份数 × 每份至少。
- 每次领到发多少由代码定。每一份有一个能发的范围，代码返回的金额（整数分）拉进这个范围：

| | 最少 | 最多 |
|---|---|---|
| 不是最后一份 | 每份至少 | 剩余奖池 −（剩余份数 − 1）× 每份至少 |
| 最后一份 | 剩余奖池 | 剩余奖池 |

- 最后一份发完剩下的全部，不管代码返回多少（用户定），所以领完不会有剩。到截止时还有份没人领，剩下的退回🐟额。
- 例子：总奖池 100.00、10 份、每份至少 0.01，代码每次返回 100（1.00）：前 9 份各 1.00，第 10 份发 91.00。代码给得少，最后一份就大，可能有人故意等到最后才领；不想这样，代码自己把钱摊开。开发包的模拟会列出每一份发多少。
- 被拉进范围时（多了封顶，少了保底，或者是最后一份），代码给的数和实际发的数都记下。领的人在自己的结果里看到“按上限发”“按每份至少发”或“最后一份，发完剩下的”；红包作者在记录里看得到两个数。
- 名单照旧公开昵称、时间和金额。

## 3 领取

- **在哪领**：只在红包页。点「开」展开指令框，作用域标签是黑金的“代码判定 · 标题”，输入用等宽字。必须输入，没有直接领。首页不匹配（做不到：要跑每个红包的代码），所以和关闭首页领取的红包一样，强制加入红包广场。分享文案同关闭首页领取：写红包页地址和红包作者的提示。
- **输入**：单行，1–200 个字。首尾空白去掉，其余原样：区分大小写，空格和符号都算，没有口令框的“优化”。粘贴（或拖进来）的多行文字，换行换成一个空格：连续的换行（含空行）连同两边的空格和制表符，合起来只换一个空格；代码收到的仍是一行（2026-10-27：有的玩法要领的人整段粘贴多行的分享文案，比如每日 Bingo 的 7 行，由代码从里面找链接）。框上方是红包作者写的提示（最多 40 个字），下方写“原样提交：区分大小写，符号都算，首尾空格会去掉”（换过换行时换成另一句，见 [02](redesign/02-shell.md) 第 4 节）。输入照旧不进地址栏、浏览历史和浏览器存储。
- **顺序**：登录、不是自己发的、领取范围、尝试间隔（活动页默认 2 秒）、人机验证（打开时）都照旧先查，不过的不调用代码；过了再交给代码判定，按判定发钱。
- **人机验证**：红包作者打开“领取前人机验证”时，每次提交都要先通过验证，再交给代码判定（用户定）。口令红包是口令对了才弹验证；这里要跑了代码才知道对不对，所以没法只在“会受理”时才弹。
- **回复**：代码返回的 `message` 是给领的人的一句话，发不发都用它（纯文字，最多 100 个字），标明“代码的回复”；领到时显示在他自己的结果里。
- **我的提交**（2026-10-24 用户提出）：每次被判定的输入、回复和结果都留在红包页上，只有自己看得到（[05](redesign/05-hongbao.md) 第 3 节），回头翻得到之前的回复，靠回复给提示的玩法（猜数字的“大了”“小了”）才玩得下去。
- **试几次**：平台不限次数，也不替代码拦人（用户定：“每人最多提交几次”的设置和“不能再试”的标记都不要，增加复杂度，心智负担也大）。要限次数，代码按传进去的“被判定过几次”自己拒绝，在回复里写清楚。
- **出错和超时**：代码出错或超时，这次不算领取，也不算被判定过一次，提示“红包的代码出错了，请稍后再试”。连续 5 次就自动暂停领取，并通知红包作者；暂停以后，红包作者可以提前结束，剩下的退回。除此以外，提前结束的规则照旧（有人领过就不能）。
- **排队**：同一个红包的提交在它的 Durable Object 里排队，一次只判定一个。剩余奖池、已领记录、代码的状态都由平台传进去，代码不靠全局变量记东西。每个红包每秒最多受理 20 次提交（暂定），超出的请对方稍后再试，不调用代码。联网的另有排队上限（第 9.3 节）。
- **尝试统计**：照旧记下每次的输入，只给红包作者看。

## 4 代码协议（第一版）

- **两个文件**（2026-10-24 用户指出测试要和代码分开）：
  - `judge.js`：线上跑的、算指纹的、结束后公开的只有它。ES 模块，最大 64 KB，导出判定函数 `judge(submission, tools)`，可以是 async。不叫 `claim`：领取是领的人在做的事，代码做的是判定（用户定）。
  - `tests.json`：测试，只是数据，平台不当代码跑；不算进指纹，不公开（第 5 节）。指纹和 Dynamic Worker 只认代码，改测试不会多出一个 Dynamic Worker；也不用在代码里摇树分离。
- **金额**都是整数，单位是分（0.01），不带币种：现在只从🐟额发，以后可能接 LDC 商户（用户定）。字段名不带单位，同 Stripe 的写法，文档写明。**时间**都是毫秒。

### 4.1 传进去的

```ts
interface Submission {
  input: string;      // 领的人输入的：已去掉首尾空白，1–200 字
  now: number;        // 判定时间（服务器时钟）；代码里 Date.now()、new Date() 都是它
  user: {
    id: number;       // LINUX DO 数字 ID
    username: string;
    level: 0 | 1 | 2 | 3 | 4 | null; // 信任等级（上次登录时取的），没有时 null
    attempts: number; // 他在这个红包里之前被判定过几次（出错、超时不算）
  };
  hongbao: {
    title: string;
    total: number;          // 总奖池
    count: number;          // 总份数
    minEach: number;        // 每份至少
    remaining: number;      // 剩余奖池
    remainingCount: number; // 剩余份数（含这一份）
    openedAt: number;
    endsAt: number;
  };
  share: { min: number; max: number; last: boolean }; // 这一份能发的范围（第 2 节）
  claims: {                 // 已领到的，按先后
    user: { id: number; username: string };
    amount: number;
    input: string;
    at: number;
  }[];
  state: Json | null;       // 代码上次存的，最开始是 null
}
```

- **交给代码的，等于交给红包作者**：代码能把收到的东西写进状态或回复，所以只传领的人愿意让红包作者知道的。名单上本来就有的（数字 ID、用户名）、他自己输入的、等级（用户定：传，能做“按等级给”；领取范围本来就能按等级限人）。已领记录里别人的输入，红包作者本来就看得到。
- 领过的人、领取范围以外的人，都走不到代码；红包作者自己也能领（[自领](self-claim-design.md)）。

### 4.2 返回的判定

```ts
interface Verdict {
  ok: boolean;         // 发还是不发
  amount?: number;     // ok 时必填：整数分，平台再拉进 share 的范围
  message?: string;    // 给领的人的一句话，发不发都用它；纯文字，最多 100 字
  state?: Json | null; // 写了就整个换掉（发不发都存），不写就不变；最大 16 KB，最多嵌套 100 层
}
```

- 单独一个 `ok` 表示发不发，一句话只有 `message` 一个字段（用户定）。
- `ok: false` 时 `amount` 不看。低于 `share.min` 按 `min` 发，高于 `max` 按 `max` 发，最后一份发完剩下的；不想发就返回 `ok: false`。
- 状态发不发都能改（用户定）。代码能记住谁答错过什么，不用全靠 `attempts`。
- `message` 里的换行和连续空白合成一个空格。不认识的字段忽略，检查时提醒一句，免得拼错了没发现。
- 算出错的：`ok` 不是布尔值；发的时候 `amount` 缺了或不是整数；`message` 超过 100 字；`state` 转不成 JSON、超过 16 KB 或嵌套超过 100 层。

### 4.3 能用的

- **Web 标准**都能用：完整的 `crypto`（含 `getRandomValues`、`randomUUID`，用户定）、`Intl`（能按时区算时间）、`TextEncoder`、`URL`、`atob`、`btoa` 等。去掉 `caches`：它可能让数据在不同红包之间流动。第一版不能联网，联网会报错；第二版见第 9 节。
- **Node 模块**（`nodejs_compat`，2026-10-24 实测）：`node:crypto`、`node:buffer`、`node:util`、`node:zlib`、`node:path`、`node:querystring`、`node:string_decoder`、`node:assert`、`node:url`、`node:events`。
  - 写法是文件开头的静态 import，必须带 `node:` 前缀，比如 `import { createHmac } from "node:crypto"`。模块是运行时自带的，不安装、不打包，不算进 64 KB。
  - 其余模块（fs、net、http、dns、os、process、child_process、worker_threads、vm 等）要么碰外部世界，要么在这里没有意义，不许 import。
  - 不能 import 别的文件、npm 包或网址；想用第三方库，就把要用的部分放进 `judge.js`，或者自己打包成一个文件再贴，公开的就是贴上来的那份。
  - 不能用动态 `import()`（模块名能在运行时拼出来，检查不了），也没有 `require`。
  - 检查时用 JS 解析器列出所有 import，不在清单里的拒绝。沙箱本来就断网、没有密钥，文件系统是虚拟的（只有代码自己和一个临时目录），这一步主要是把话说清楚。
- **`console`**：线上直接丢弃，只在开发包里看得到（用户定）。

### 4.4 随机数

- **种子**：开放时本站生成 32 字节的秘密种子 S（64 位十六进制），公布封存值 `SHA-256("hb.lafi.sh/judge/v1\n<红包 ID>\nS")`，写法同开奖证明的拼手气。结束前谁都不知道 S，红包作者也不知道：他要是知道，就能算出“谁第几次提交会抽到什么”，代码看着公平却暗中照顾人。沙箱里也只拿得到下面两个子种子，拿不到 S。
- **两条流**（用户定）：
  - `tools.random`：这一次提交的。子种子 `SHA-256("hb.lafi.sh/judge/v1/random\n<红包 ID>\nS\n<用户 ID>\n<attempts>")`。同一个人每次提交拿到的都不同，别人怎么提交也影响不到。`Math.random()` 也用它。
  - `tools.userRandom`：这个人固定的。子种子 `SHA-256("hb.lafi.sh/judge/v1/user-random\n<红包 ID>\nS\n<用户 ID>")`。同一个人不管提交几次都拿到同一组，适合“每人抽一次签”。
  - 字节流同开奖证明第 2 节：`SHA-256("<子种子>:0")`、`SHA-256("<子种子>:1")`……接起来按顺序取。`next()` 取 53 位，`int()` 用拒绝采样不偏；同一次判定里所有的随机调用按调用顺序往下取。
- 同一个种子、同一个人、同一个第几次，本地和线上取出来的数一模一样；测试里可以指定种子。代码出错或超时不算一次判定，重试拿到的还是同一组数，不会因为出错换一次运气。
- 按每次提交的流，人能靠反复提交重新抽：只要代码在拒绝时露了随机结果，就要按 `attempts` 限次数，或者改用 `userRandom`。
- `crypto` 和 `node:crypto` 的随机是真随机，能用，但重放对不上，开发包会提醒。
- 本站开放时就知道种子，这和拼手气一样；能证明的是种子开放后没换过。

### 4.5 `tools`

Node 和 Web 标准里已有的摘要、编码不重复给，只给红包特有的。全是同步的，本地和线上同一份实现。

```ts
interface Tools {
  random: Random;      // 这一次提交的流（4.4）
  userRandom: Random;  // 这个人固定的流（4.4）
  money: {             // 都按这一份的范围算，返回整数分
    even(): number;    // 剩余平均：剩余奖池 ÷ 剩余份数，向下取整
    lucky(kind?: "double" | "bounded"): number; // 同拼手气：微信同款（二倍均值）/ 支付宝同款（均值上下 50%），用 random
    format(amount: number): string;             // 2000 → "20.00"
  };
  code: {              // 口令
    personal(key: string, parts: (string | number)[], length?: number): string; // HMAC-SHA256 → Crockford Base32，默认 10 位
    totp(secret: string, options?: { step?: number; digits?: number; offset?: number }): string; // RFC 6238，兼容验证器 App；offset -1 是上一步
    window(seconds: number): number;            // now 落在第几个时间段
    same(input: string, code: string): boolean; // 按 Crockford 比：不分大小写，O=0、I/L=1，忽略空格和横线
  };
  text: { normalize(text: string): string };    // NFKC、去零宽字符、合并空白、转小写
  time: {
    parts(timeZone?: string): {                 // now 在某个时区的日期时间，默认 Asia/Shanghai
      year: number; month: number; day: number; hour: number; minute: number; second: number;
      weekday: number };                       // weekday：1 是周一，7 是周日
  };
}

interface Random {
  next(): number;                         // [0, 1)
  int(min: number, max: number): number;  // 含两端
  pick<T>(items: T[]): T;
  shuffle<T>(items: T[]): T[];            // 返回打乱后的新数组
}
```

### 4.6 出错

| 情况 | 领的人看到 | 红包作者看到 | 算一次判定吗 | 算连续出错吗 |
|---|---|---|---|---|
| 不发（`ok: false`） | 代码的回复 | 尝试统计里有 | 算 | 不算 |
| 代码抛错 | 红包的代码出错了，请稍后再试 | 出错记录：时间、错误信息 | 不算 | 算 |
| 超时 | 同上 | 记“超时” | 不算 | 算 |
| 返回不对（4.2） | 同上 | 记哪里不对 | 不算 | 算 |
| 平台的沙箱不可用 | 暂时领不了，请稍后再试 | 不记，不是代码的错 | 不算 | 不算 |

连续出错 5 次自动暂停（第 3 节）。

### 4.7 限制和版本

- 每次判定 CPU 50 毫秒（线上实测约 2 秒才会被杀，第 7 节），平台最多等 300 毫秒，到点按超时算。代码 64 KB，状态 16 KB（最多嵌套 100 层：JSON 序列化是递归的，能到多深看机器的栈，定死了网站和开发包才一致；2026-10-25 用户定），一句话 100 字，输入 200 字，测试 200 条。
- **协议版本**：第一版是“兼容日期 2026-09-01 + `nodejs_compat` + 本站的外层和 `tools`”。开放时记下用哪一版，老红包一直用它；Cloudflare 以后改了运行时的行为，也只影响新版本。开发包按协议版本发布，版本对不上时提醒。第二版加上联网（第 9 节）。

## 5 开发和检查

- **第一版只做本地开发包**（用户定），不做浏览器里的运行环境。开发包放在主仓库，用 MIT 许可（主仓库是 AGPL，红包作者照模板写的代码不受牵连），按协议版本发布。外层、能用的、`tools` 和结果校验都和线上同一份。四个命令：`npm test` 跑 `tests.json`，`npm run check` 照网站部署时的规则查一遍，`npm run simulate` 让一批虚拟的人来领，`npm run replay` 用下载的完整记录重放核对（输出见下）。
- **开发包的样子**（2026-10-24 定，第 4 步）：仓库的 `kit/` 目录本身就是一个能直接用的项目，红包作者整个拿走（`npx degit LeUKi/hb/kit 我的红包`，或下载仓库压缩包取出 `kit`），`npm install` 以后就能跑。
  - 文件：`judge.js`、`tests.json`、`simulate.json` 三个模板（一个能跑通的示例玩法），`tests.schema.json`、`simulate.schema.json`（两个 JSON 的格式），`judge.d.ts` 和 `jsconfig.json`（`tools` 和允许的 Node 模块都有类型提示，编辑器和 AI 都看得到能用什么），`AGENTS.md`、`.claude/skills/hongbao-judge/SKILL.md`、`.cursor/rules/hongbao-judge.mdc`（给 AI），`runtime/`（沙箱里那部分，网站用同一份），`cli/`（四个命令），`README.md`（怎么开始）。
  - 只依赖 `wrangler`（版本和网站一致）：命令通过它自带的 miniflare 起本地的 workerd，兼容日期、`nodejs_compat`、外层和 `tools` 都和线上一样；网络关掉，和线上一样连不出去。
  - 本地不限 CPU，每次判定按时间掐断：超过 1 秒算超时（线上是 50 毫秒 CPU、等 300 毫秒），超过 50 毫秒的标“慢”，提醒线上可能超时。
- **四个命令的输出**（中文，失败时退出码非 0，方便 AI 和脚本判断）：
  - `npm test`：先按部署时的规则查 import，不过就列出第几行什么问题、不跑测试；然后每条一行“✓ 名字（3 毫秒）”或“✗ 名字：哪里不对”（多步的写到第几步、谁），不对时写出代码实际返回的；`console` 输出缩进跟在那一条下面；最后“测试 N / M 通过”。`npm test -- 名字` 只跑名字里含这几个字的。
  - `npm run check`：和网站部署时同样的几行（import 都在清单里、代码能加载并导出了 judge、测试 N / M 通过），每条跑两遍、结果不一样的提醒“用了真随机，线上没法重放”，再写文件大小和代码指纹（和网站上展开代码时显示的一致，能对上）；最后“可以去网站部署了”或“还不能开放”。
  - `npm run simulate`：按 `simulate.json` 里的先后，一个个人来提交，状态、已领记录、剩余奖池都像线上一样往下传，金额照样拉进范围；一行一次提交：第几次、谁、输入、结果（领到 0.30 / 没领到 / 出错 / 已领过 / 已领完）、代码给的和实发的（不一样时写原因）、代码的回复；最后“发出 X / 总奖池 Y，领了 N / M 份，剩下的退回”。随机数用固定种子，同一份文件每次结果一样；`--seed` 换一个。
  - `npm run replay -- judge-records-xxx.json`：先核对本地 `judge.js` 的指纹和记录里的一样、种子和封存值对得上，对不上就说清楚并停下；然后逐条重放，比 `ok`、代码给的金额、回复和状态，“第 N 次判定 一致”或写出哪一项不一样；最后“N 次判定全部一致”。
- **`tests.json`**（2026-10-24 用户定稿：原来能写出线上不可能的情况、期望太少、测不了靠状态往下传的玩法）：一个对象，`tests` 是测试的数组；第一行可以写 `"$schema": "./tests.schema.json"`，开发包带这份 JSON Schema，编辑器和 AI 写的时候就能补全、标错。
  - **一条测试就是一次提交**，字段和代码收到的 `submission` 一一对应、同名，没写的用默认值：

    | 字段 | 写什么 | 默认 |
    | --- | --- | --- |
    | `name` | 测试的名字，最多 100 个字，不能重名 | 必填 |
    | `input` | 提交的输入，规则同线上（一行、1–200 个字、去掉首尾空白） | 必填 |
    | `now` | 这次提交的时间，毫秒或 ISO 时间 | 2026-10-24 12:00（北京时间） |
    | `user` | `id`、`username`、`level`（0–4 或 null）、`attempts`（被判定过几次） | 10000、tester、2、0 |
    | `hongbao` | `title`、`total`、`count`、`minEach`、`openedAt`、`endsAt`（时间同 `now` 的写法） | 测试红包、10000、10、1、`now` 前 1 小时、`now` 后 1 天 |
    | `claims` | 前面已领的份：数字（补上占位记录，每份平均）或完整列表（`user` 的 `id`/`username`、`amount`、`input`、`at`） | 没人领 |
    | `state` | 代码之前存的状态 | null |
    | `seed` | 种子（64 位十六进制） | 固定的测试种子 |

    剩余奖池、剩余份数和这一份的范围由 `claims` 推出来，不能直接写。
  - **只能写线上可能出现的情况**，不然这条测试本身不通过，说清楚哪里不对：`now` 在开放和截止之间；已领的时间按先后、不早于开放、不晚于 `now`；每份不少于每份至少，剩下的够剩下每份都拿到每份至少；还有没领的份；已领的人不重复，这个人不在里面；`state` 不超过 16 KB、嵌套不超过 100 层；总奖池够每份都拿到每份至少。
  - **多步场景**：不写 `input`，写 `steps`，几个人依次提交：每一步 `{ "who": "小明", "input": "…", "expect": {…} }`，可选 `level`（默认 2）、`at`（默认上一步往后 1 分钟，第一步是 `now`）。同一个 `who` 是同一个人；状态、已领记录、每人被判定过几次、剩余奖池都像线上一样一步步往下传（和 `npm run simulate`、`npm run replay` 同一套推进）。已经领过的人、或者份已经领完了还要提交，这一步算不通过（线上根本不会交给代码）。`hongbao`、`claims`、`state`、`seed` 写在测试上，是第一步之前的样子。
  - **`expect`**：`ok` 必填；其余写了才比：`amount`（实际发的，拉进范围以后）、`asked`（代码自己给的）、`note`（拉进范围的原因 `"cap"`、`"floor"`、`"last"`，没拉写 `null`）、`message`（逐字）或 `messageIncludes`（含这几个字）、`state`（整份，键的顺序不算）或 `stateIncludes`（只比写了的键，数组整个比）。没发（`ok: false`）就不能写金额几项。代码返回协议以外的字段也算不通过。不一样的地方一起列出来，不只说第一处。
  - **数量**：所有测试加起来最多判定 200 次（一步算一次）。
- **`simulate.json`**：`{ "$schema": "./simulate.schema.json", "hongbao": { …同 tests.json… }, "seed": "…", "submissions": [ { "who": "小明", "input": "flag{…}" }, … ] }`，每次提交的写法同多步场景的一步，只是没有 `expect`。和场景不同的是，已经领过的人、领完以后的提交不算错，照实写“已领过”“已领完”。
- **给 AI 的材料**：大多数红包作者会用 AI 写代码（用户判断）。开发包里放 `AGENTS.md`（协议、限制、能用的模块和 `tools`、`tests.json` 怎么写、例子、常见错误：顶层用 `Date.now()`、真随机、返回小数金额、状态写太大；写完先跑 `npm test` 和 `npm run check`，全过再贴到网站）、Claude Code 的 skill 和 Cursor 的规则（只是指向 `AGENTS.md` 的短说明，内容不重复）；网站上的“给 AI 的说明”是一段能整段复制给聊天 AI 的提示词，开头列出开发包、`AGENTS.md` 的纯文本地址和 `/help/code`（2026-10-25 用户要求，让 AI 代理自己找到全部资料；`/help/code` 是浏览器里渲染的页面，直接抓取读不到内容，所以代理读的是 `AGENTS.md`）。不做 MCP 之类的接口，最后一步总是在网站上粘贴代码（用户定）。
- **部署**（2026-10-24 用户定，取代原来的“在线检查”；用户觉得原来的界面太容易随手改代码，改了也意识不到）：网站上的代码不是随手改的字段，而是要部署的一份东西。部署就是把这一版代码做成**判定器**：放进和线上同一个 Dynamic Worker（ID 是协议版本加代码指纹），跑一遍 `tests.json`；开放以后，每次提交都交给开放时的那个判定器判定，不能再换。
  - 部署时查这几样：能加载、导出了 `judge`、import 都在清单里、没有动态 `import()`、文件大小、测试全过；每条测试跑两遍（多步的整个场景跑两遍），结果不一样就提醒（用了真随机）。“最慢 N 毫秒”只算判定本身：先记用量，再像开发包一样预热判定器（加载 judge.js 不计时，同一天同一个判定器不多算份），然后才开始计时（2026-10-25 用户发现线上显示 223 毫秒、本地 3 毫秒后定）。开放前必须有一个部署过、测试全过的判定器，开放用的就是它。
  - **费用**：部署一个新版本，当天就算一份 Dynamic Worker（第 7 节）；同一天重新跑测试、开放后领取都还是这一份，隔天再用才再算。部署时有测试超时，换一个新的运行实例接着跑，最多换一次，再超时剩下的测试就不跑，写“前面超时，这条没跑”：一次部署最多算 2 份（2026-10-24 用户定）。领取时超时照旧最多换到第 4 个。
  - **版本**：这个红包里每部署一份新代码就是新的一版，按先后叫“第 1 版”“第 2 版”（用户定：不显示哈希）。还没部署的代码不编号，写“新代码 · 未部署”；贴回一份部署过的代码，认得出来，还是原来的版号，不用再部署。代码指纹只在展开代码时附一行小字，方便和本地 `npm run check` 对上。
  - **次数**：只有部署新版本才算一次，每人每天 10 次（站长可调）；只改测试在同一版上重新跑、换回部署过的版本，都不算。部署和重新跑测试在开始跑之前就记下，中途断开也算；运行环境出了问题没跑成也算（代码能故意引起它），写“判定器的运行环境暂时不可用，请稍后再试；这一版再跑不另算次数。”。次数按人和代码算：自己在别的红包部署过的代码，在这个红包里还是新的一版，但不扣次数。另有一个不显示的上限，每人每天最多跑 50 次（部署和重新跑测试都算），只防有人刷。一个人同一时间只跑一份：上一次还没跑完再按，写“上一次测试还在跑，等它跑完再试。”，免得几份一起跑都没算进次数。
  - **换回**：草稿把这个红包最近部署的 10 版（版号、指纹、部署时间、上一次跑的是哪份测试、过没过）存在服务端，和代码一样加密；换回要用的那一版（最近一个测试全过的）连代码一起存。代码换了以后能一键换回，刷新页面也还在；那一版上一次跑的就是现在的测试并且全过，换回后直接能开放，否则要重新跑测试。
  - 开放时还没有测试全过的判定器，写“还没有测试全过的判定器，草稿已保存。”；这一版部署过、只是现在的测试没在上面跑过，写“测试改过了，要重新跑一遍，草稿已保存。”。

## 6 透明和核对

- 开放时公布代码的指纹和种子的封存值（第 4.4 节）。总奖池、份数、每份至少本来就在红包页上，开放后不能改。
- 红包皮上公开代码已经判定了多少次，名单每行写第几次领到；参与名单里的“挑战”公开每个被判定过的人、判定了几次、最近一次的时间和领到没有（2026-10-25 用户定，[05](redesign/05-hongbao.md) 第 4、7 节）。第一次提交前在输入框下说明这一点。
- 结束后对所有人公开代码和随机种子，谁都能核对代码没换过。名单照旧（昵称、时间、金额），每份写明有没有被拉进范围。哈希写法同开奖证明（SHA-256、各项换行分隔），方便手算。
- 不公开任何人的输入，也不公开代码存的状态，因为状态里可能记着输入（2026-10-24 用户指出领取记录会带上别人的输入，改成这样）。口令红包结束后虽然公开全部口令，但谁用了哪个，只有本人和红包作者看得到；代码判定红包还可能让人输入任何东西。代价是别人没法独立重放全部领取，公开核对只到“代码没换过、钱的账对得上”。
- 红包作者能下载完整的领取记录（每份领到时交给代码的数据，含输入和状态），用开发包重放。这和现在一样：口令红包的名单弹窗里，红包作者本来就看得到每个人用的口令。
- 领的人在“我的提交”里看得到自己每次交的输入和代码的回复；种子公开后，他知道自己的 ID 和第几次提交，能算出自己那几次拿到的随机数。联网的红包结束后，还看得到自己那几次判定的返回（第 9.4 节）。

## 7 运行：Dynamic Workers

- 每份代码一个独立的 isolate：不给任何绑定和密钥，网络断开（`globalOutbound: null`；第二版联网的红包接到本站的网关，第 9.7 节），打开 `nodejs_compat`，兼容日期按协议版本。模块是开发包 `kit/runtime/` 的沙箱部分（`bun scripts/judge-runtime.ts` 复制进 API，测试会检查是否最新）加上 `judge.js`；入口 `main.mjs` 先加载 `prelude.mjs`，代码之前就固定好时间、`Math.random()`、`console`，去掉 `caches`。
- isolate 的 ID 是 `judge:v<协议版本>:<代码指纹>`：同一份代码一天里调用多少次都只算一个，几个红包用同一份代码也只算一个，只改测试也不会多一个。协议开放后，这一版的运行时就不再改，改了算新版本，老红包一直用开放时那一版。第一版 2026-10-25 起冻结（生产上第一个代码判定红包开放），`scripts/test/judge-runtime.test.ts` 对运行时的副本核对固定的哈希。
- 超时以后，下一次换一个新的 isolate，免得排在卡住的那个后面；运行时当场掐掉的（在等一个永远不会完成的 Promise）没有卡住什么，接着用原来那个。
- **用量记录**（2026-10-24 用户定，站长要能监控、管住这块开销）：一个判定器（isolate 的 ID 加代码）在某个 UTC 日第一次被用到时记一份，和 Cloudflare 的计费单位一致；同时记是谁的、哪个红包（还没开放的部署记在红包作者身上）、为什么用（部署、重新跑测试、领取）、跑了几次、超时几次、其中换了几次实例。日期按这次第一次用到它的时间算（跨过 UTC 0 点的一次部署记在前一天）。部署和重新跑测试在第一次用到这个判定器之前先记下（中途断开也照记），领取时并进本来就有的那批写入，领取出错也照记。保留最近 90 天，由维护任务“判定器用量清理”删掉更早的。这是本站按记录估算的，账单以 Cloudflare 为准。
- **每月上限**：站长设“每月判定器上限（份）”，默认 1000（免费额度）。本月份数到了上限，新版本暂时不能部署（红包作者看到“本月判定器用量到了上限，新版本暂时不能部署。”），重新跑测试也不行（“本月判定器用量到了上限，暂时不能重新跑测试。”），除非它当天已经记过一份；已经开放的红包照常领取，不因为额度卡住别人的钱。站长调高上限就恢复。几个人恰好同时部署时可能略超一点（每人一次最多 2 份）。
- **费用**（官方价格，2026-06）：按“代码 × 天”计，每月 1,000 个免费，之后每个 0.002 美元；请求和 CPU 按 Workers 原价，算在现有套餐里。正式的红包每开一天算一个，测试都在本地，部署新版本限次数，所以几乎不花钱。
- **实验**（2026-10-24，单独的实验 Worker `hongbao-code-lab`，不碰线上服务；用户同意留着以后再测）：
  - 第一次加载 15–20 毫秒，之后不到 1 毫秒到几毫秒；在 Durable Object 里连续判定 12 次，第一次 18 毫秒，之后每次不到 1 毫秒，状态靠参数一路传对。
  - 断网有效，`eval` 被禁，环境变量是空的。
  - 吃爆内存只死沙箱自己，下一次照常。
  - CPU 上限要到“设的值 + 约 2 秒”才杀（设 10、50、200 毫秒都是约 2.2 秒），所以平台要在外面自己计时；死循环时调用方不受影响，但后面对同一份代码的调用会排在它后面。
  - 运行中 `Date.now()` 不走；本地会走，本地也不限 CPU。本地的沙箱和调用方似乎在同一个线程，死循环会把本地测试整个卡住，所以本地测超时用一个不回答的假沙箱；线上调用方的计时器照常走。
  - API 的测试环境（`@cloudflare/vitest-plugin`）能跑真的 Dynamic Worker：断网、Node 兼容都生效，沙箱的测试直接用它。
  - 语法错在加载时就报出来，部署时就能查到。
  - 出网网关（第二版要用）：只放行声明的网站，11 毫秒；别的网站被拒。
  - 打开 `nodejs_compat` 后，`node:crypto`（md5、sha256、HMAC）、`Buffer`、`node:util` 等都能用，按时区取时间、NFKC 也正常；第一次加载约 30 毫秒（不开时 15–20 毫秒），之后约 4 毫秒。

## 9 第二版：联网（2026-10-26 定，2026-10-26 实现）

用户提出（2026-10-26）：判定器可以联网，比如把提交转给红包作者自己的接口，由对方的服务器判定或承担运算。做成协议第二版的一个配置项。界面也写进了界面规范：[05](redesign/05-hongbao.md) 第 3、4、9 节，[02](redesign/02-shell.md) 第 4 节，[07](redesign/07-pages.md) 第 5、10 节。迁移 0045。

### 9.1 第二版

- 第二版就是第一版加上联网，其余都不变：兼容日期、`nodejs_compat`、传进去的和返回的、`tools`、限制（第 4 节）。
- 上线以后，新开放的代码判定红包都用第二版，联网和不联网的都是（用户定）。已经开放的留在第一版，第一版不再改（第 7 节）；开发包保留第一版，老红包照样能重放。
- 上线时还没开放的草稿：在第一版上部署过的版本，要在第二版上重新跑一遍测试才能开放，不算部署次数。

### 9.2 白名单

- **写在代码里**：`judge.js` 导出 `network`，列出能请求的地址前缀，最多 3 条（用户定）。不导出就不联网，和第一版一样断网。

  ```js
  export const network = ["https://api.example.com/hongbao/"];
  ```

  - 开发包和网站认的是同一份：改白名单就是改代码，要部署新版本。
  - 开放后跟着代码固定，结束后跟着代码公开。
- **每条的写法**：
  - `https://` 开头的完整域名加路径前缀。
  - 不带端口（只走 443）、用户名密码、`?` 和 `#`。
  - 不许 IP 地址、`localhost` 和不带点的主机名；不许 linux.do 和它的子域名，也不许本站域名（hb.lafi.sh 和它的子域名）。
- **不做网站归属验证，也不做签名**（用户定）。
- **怎么算匹配**：
  - 请求地址先按 URL 标准规范化，`..` 和 `%2e%2e` 会先被消掉。
  - 然后协议和主机要相同、端口是默认的，路径以前缀开头并且断在 `/` 处：前缀 `https://a.com/api` 放行 `/api`、`/api/x`、`/api?x`，不放行 `/apix`。
  - 路径里有编码过的斜杠或反斜杠（`%2f`、`%5c`）一律拒绝，免得对方服务器解码以后跳出前缀。
- **部署时查**：
  - 每条合规、不超过 3 条。
  - 网站管理的联网开关关着时，导出了 `network` 的代码不能部署，写“代码判定暂时不能联网。”。

### 9.3 发请求

- **直接用标准的 `fetch`**（用户定）：`Request`、`Response`、`AbortSignal` 都能用，不放进 `tools`。限制都在沙箱外面，代码怎么写都绕不过去。
- **限制**：
  - 每次判定最多 3 个请求（用户定），可以并发；这次判定结束后再发的请求一律拒绝。
  - 只许 GET 和 POST，请求体最大 16 KB。
  - 单个请求 3 秒超时。联网的红包每次判定最多 5 秒；CPU 照旧 50 毫秒，等网络的时间不算 CPU。
  - 平台的计时在有请求在路上时暂停：不在等网络的时间照样最多 300 毫秒，和不联网的红包一样，超过按超时算（2026-10-26 用户定：等网络不能换来更多计算时间；运行时要到约 2 秒才杀，单靠它管不住，第 7 节）。
  - 返回最大 64 KB，超过算失败。跳转不跟随，3xx 原样交给代码。
- **请求头**：
  - 代码可以随便设，`Host` 和 `X-Hb-` 开头的除外。
  - 网关加上 `User-Agent: hb.lafi.sh-judge (+https://hb.lafi.sh/help/code)` 和 `X-Hb-Hongbao: <红包 ID>`。后者不保密，只是方便对方分清是哪个红包。
  - 返回里的 `Set-Cookie` 去掉。
- **红包作者自己防绕过**：
  - 对方的接口在公网上，领的人可以绕过本站直接去问它，那样没有尝试间隔，也没有人机验证。
  - 要防，就在代码里放一个只有自己知道的令牌，请求时带上，接口只认带令牌的请求。
  - 代码结束后公开，令牌也会跟着公开，结束后要作废。第 3 步、帮助页和 `AGENTS.md` 都写明这一点。
- **失败**：
  - `fetch` 抛错（`TypeError`），错误信息写明原因：“联网失败：这个地址不在白名单里：https://…”“联网失败：超时（3 秒）”“联网失败：返回超过 64 KB”“联网失败：这次判定已经发了 3 个请求”“联网失败：连不上对方”“联网失败：只能用 GET 和 POST”“联网失败：请求体超过 16 KB”“联网失败：不能设请求头 …”；没导出 `network` 是“联网失败：这个红包没有联网（judge.js 没有导出 network）”，在 `judge` 外面或判定结束后是“联网失败：fetch 只能在 judge 运行时用（判定结束以后也不行）”。
  - 代码可以接住，自己回复领的人；没接住就是代码出错（第 4.6 节），连续 5 次照旧自动暂停。
  - 对方返回 4xx、5xx 不算失败，照常交给代码。
- **本站网关自己出了问题**：这次判定作废，按“平台的沙箱不可用”处理，不算判定，也不算出错。代码接住了也一样。
- **排队**：联网的判定慢。同一个红包同一时间最多 5 个提交在排队（含正在判定的），再多的请对方稍后再试：不调用代码，也不算尝试。

### 9.4 记录

- **记什么**：网关记下每次判定的每个请求：方法、完整地址、请求体、返回的状态码、内容类型、返回内容（最大 64 KB）、用时，失败时记原因。和这次判定的输入一样加密，存进判定记录（用户定：要能完整重放）。
- **红包作者**：完整记录里有全部请求和返回，可以下载，用 `npm run replay` 照记下的返回重放。
- **领的人**：
  - 红包结束后，在“我的提交”里展开自己的某一次判定，能看到那次每个请求的返回：网站（主机名）、状态码、返回内容（默认收起），失败的写原因（用户定，2026-10-26）。
  - 看不到请求本身，因为地址和请求头里可能有令牌；也看不到别人的。
  - 结束前只有代码的回复。
- **其他人**：照旧，结束后公开代码和种子，不公开输入、状态和返回（第 6 节）。

### 9.5 公开说明

- **红包皮**：多一个“联网”标签，悬停或点按时说明：“判定时会请求这些地址：…。判定结果取决于对方的回答，开放后对方的回答可能变化，本站无法核对。”
- **代码一节**：列出白名单。
- **第一次提交前**：输入框下的说明多一句“这个红包会联网：你的提交（数字 ID、用户名、等级和输入）可能被发到 api.example.com。”
- **发红包第 3 步**：部署后从代码读出白名单，列在代码下面（“联网：…”），再写三句：
  - 领的人提交的内容可能被发到这些地址；
  - 结束后代码公开，写在代码里的令牌也会公开，结束后请作废；
  - 红包结束后，领的人能看到自己那几次判定的返回内容，别在返回里放不想公开的东西。

### 9.6 开发包

- **`tests.json`**：
  - 每条测试（多步的每一步）可以写 `fetch`，列出这次判定会收到的返回，最多 3 个，每个写成 `{ "url": "…", "method": "GET", "status": 200, "headers": {…}, "json": … }`，`json` 和 `text` 二选一；写 `{ "url", "method", "error": "timeout" | "unreachable" | "too-big" }` 就是这个请求失败。`simulate.json` 的每次提交同样能写。
  - 代码发出的请求按方法和完整地址依次对上。有请求没写到返回，或者写了的返回没用上，这条测试都不通过，并写清是哪一个。
  - 限制和白名单照线上查。
- **测试从不真的联网**：本地 `npm test` 和网站部署时跑的测试都只用 `fetch` 里写的返回，结果才稳定。
- **`npm run simulate`**：`simulate.json` 的每次提交也可以写 `fetch`。加 `--live` 就从红包作者自己的电脑真的发出去，照样查白名单和限制，带同样的 `User-Agent`，`X-Hb-Hongbao` 写 `local`。
- **`npm run replay`**：先比代码这次发的请求（方法、地址、请求体）和记录里的一不一样，再用记下的返回比判定。第一版开放的红包用第一版的运行时重放（开发包里冻结的一份 `runtime/frozen/v1.json`，网站用的也是它）。
- **`npm run check`**：多列一行白名单，逐条写合不合规。

### 9.7 运行

- **测试和不联网的红包**：判定器照旧是 `judge:v2:<代码指纹>`，网络断开。测试时由本站在沙箱里的外层，按 `fetch` 里写的返回回答。
- **联网的红包开放以后**：
  - 每个红包一个判定器，ID 是 `judge:v2:<代码指纹>:<红包 ID>`。出网（`globalOutbound`）接到本站 API 里的网关。
  - 网关从判定器的配置里知道是哪个红包、白名单是什么，不靠代码给的任何东西。
  - 每个请求发出前，网关先问这个红包的 Durable Object：是不是正在判定、这次已经发了几个。拿到返回后把记录交给它，和判定结果在同一批写入里存下。它也替这次判定计时：从第一个请求出去到最后一个回来，钟停着（第 9.3 节）。
  - 一个联网的红包每天多算一份判定器，可以忽略。
- **网关的安全**：每个请求都新建，不带本站的任何凭据和 Cookie。Workers 本来就连不到内网，又不许 IP 地址和本站域名，绕不回本站。
- **网站管理“判定器”页签**：
  - 加一个“代码判定联网”开关，默认关，Stage 试过再开。关着时联网的代码不能部署、不能开放，已经开放的照常领。
  - 用量记录多记联网请求数。
  - 没有每月请求上限（用户定：每次判定最多 3 个请求、最多 5 个排队，已经封住了量；出事有这个开关和单个红包的停用）。

## 10 不做

- “每人最多提交几次”的设置和代码宣布“不能再试”的标记（用户定）。
- 浏览器里的运行环境（第一版）；QuickJS（用户定）；MCP 之类的创建接口（用户定）。
- 商户直发、限时开奖式的代码判定：只做从🐟额发、即时判定。
- 分档：份额不预先分好，金额由代码定（用户定：分档能做的场景太少）。
- 联网（第 9 节，用户定，2026-10-26）：
  - 请求签名和公私钥；
  - 网站归属验证（比如放一个 `.well-known` 文件；没在 IANA 登记的名字也不合 RFC 8615）；
  - 每月请求上限；
  - 平台替红包作者保管密钥再加到请求头里；
  - 给领的人看请求本身，或者在结束前给他看返回；
  - 测试时真的联网。

## 附录：调研（2026-10-24）

**别家的做法**

| 产品 | 做法 | 借鉴 |
|---|---|---|
| 支付宝口令红包 | 一个口令大家领；会员活动用各自的手机号当个人口令；分时段换口令；连错有冷却 | 2024 年有人猜中“祝爸妈新年快乐”领走一万元：人想的口令，难猜比长度要紧 |
| QQ 红包 | 口令、问答（答错无限重试）、接龙、画图；专属红包指定给某个人 | 玩法多样，规则由平台写死 |
| 币安红包 | 平台生成口令；每人一次；连错 10 次锁 5 小时 | 公开的口令几分钟内就被聚合网站收走 |
| CTF 平台（CTFd、GZCTF） | 一题多个答案、每队的 flag 由哈希算出、前三名加分、可限尝试次数 | 每人不同的答案挡得住抄答案，挡不住分享解法；CTFd 的分数会回溯下调，钱发出去做不到 |
| Shopify Functions | 商家的代码编译成 WebAssembly，限 1,100 万条指令 | 平台给数据、代码只返回决定，和这里的做法一样 |

**技术比较**

| 做法 | 结论 | 理由 |
|---|---|---|
| Dynamic Workers | 选它 | 每份代码独立的 isolate，能限 CPU、能断网、能经网关联网；按“代码 × 天”计费，几乎不花钱；2026-03 起公测 |
| QuickJS（WebAssembly） | 不做（用户定） | 跑在本站自己的进程里，内存上限有已知漏洞，只能数步数限时，一个人业余维护，没审计 |
| 直接调红包作者的接口 | 归到 Dynamic Workers 里（第二版联网） | 单独做的话逻辑在对方服务器，没法公开核对 |
| CEL 之类的表达式语言 | 不需要 | 安全，但表达力不够；这里要的是任意逻辑 |
| Workers for Platforms、Containers | 不合适 | 前者每月多 25 美元、每改一次要部署；后者冷启动 0.6–3 秒 |
| `eval`、`new Function` | 不能用 | Workers 禁止在运行时生成代码 |
