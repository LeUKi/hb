# Cap 人机验证（2026-11-04 定）

领取前人机验证多一种方式：[Cap](https://trycap.dev)。它是开源的工作量证明验证，浏览器在后台算一小会儿题，不用点选、不用拼图。我们自己部署成一个 Worker（`cap.lafi.sh`），不经过第三方。中国大陆只要打得开红包站就能用；Turnstile 在中国大陆用不了（[业务规格](business-spec-v1.md) 2026-10-17 一节）。

状态：已实现；2026-11-04 部署到 Stage 并实测（Cap 服务、API、网页），生产还没发布。

## 1 用户定的

- **作者自己选开不开**：“领取前人机验证”仍然默认关。打开时选方式，默认选中 Cap，也可以选 Cloudflare Turnstile。
- **每次弹窗**：和现在的 Turnstile 一样，弹窗写明这是作者的要求，算完自动接着领取或报名，关掉弹窗就不领。
- **开浏览器检测**：除了算题，还在浏览器里跑 Cap 的检测脚本，拦下无头浏览器这类自动化工具。被拦的人会看到“换个浏览器试试”。
- **难度加倍**：一次 100 道题、难度 4（官方默认 50 道）。按官方测试折算，低端手机约 1.6 秒，新手机 0.4–0.8 秒。
- **现在只给红包站用，但留好口子**：服务按 Cap 官方服务端的接口和站点密钥来做，以后接别的项目、做 Cap 公益站，只要加站点。
- **页面直连 `cap.lafi.sh`**：红包站和以后接入的项目一样用公开的接口，不经红包站转发。代价是第一次验证要和新域名建连接，交答案前还有一次跨域预检，大约多 3–4 次往返。
- **社区小程序兼容**：小程序暂时不更新。小程序接口里的 `humanCheck` 仍然是“有没有人机验证”，两种方式都给 `true`；小程序的领取接口照样拒绝这类红包，旧版小程序照样显示“去红包站领”。

## 2 Cap 服务（`apps/cap`）

一个单独的 Worker：本地叫 `hb-cap`，Stage 是 `hb-cap-staging`（`staging.cap.lafi.sh`），生产是 `hb-cap-production`（`cap.lafi.sh`）。用的是 Cap 的无状态服务端库 `capjs-core`（锁定版本）。

**接口**（和 Cap 官方服务端一样，站点密钥在路径里）：

| 接口 | 做什么 |
|---|---|
| `POST /<站点密钥>/challenge` | 出题 |
| `POST /<站点密钥>/redeem` | 交答案（和检测结果），通过后发一个验证凭证 |
| `POST /<站点密钥>/siteverify` | 网站后端核验凭证：`{ secret, response }` → `{ success, scope? }`；凭证只能用一次 |
| `POST /<站点密钥>/scope/<范围>/challenge`、`…/redeem` | 同上，题和凭证都绑定这个范围，核验时带回来 |

- **范围**：红包站用 `claim:<红包编号>` 或 `register:<红包编号>`，和 Turnstile 的 action、cData 一样，凭证只认这个红包和这个动作。
- **站点**：现在写在配置 `CAP_SITES` 里：站点密钥、名字、秘密密钥的 SHA-256、允许的来源、题量和难度、检测开不开。秘密密钥本身只在用它的网站那边（红包站是 API 的 `CAP_SECRET_KEY`）。签题用 `CAP_MASTER_SECRET` 按站点派生出的密钥，一个站点的题拿到别的站点交不了。
- **存储**：每个站点一个 Durable Object（SQLite），记用过的题（防止同一道题交两次）和发出的凭证（核验时标记用过）。到期的记录由 alarm 清掉。不用 KV：先读再写不是原子的，两个请求同时来可能都通过。
- **限流**：从公网来的出题和交答案按站点和 IP 限流，每分钟 120 次（一次验证两次）；经服务绑定来的核验不限。
- **跨域**：出题和交答案只对站点允许的来源返回 CORS 头（红包站登记的是 `https://hb.lafi.sh`）；核验是服务器对服务器，不给 CORS。

## 3 红包站

- **设置**：配置里 `humanCheck: true` 之外加 `humanCheckMethod: "cap" | "turnstile"`。没有方式的老红包按 Turnstile 算（老表单页面发来的也一样，那时页面上写的就是 Cloudflare）。开放后仍然可以改，包括换方式。公开数据里带上方式。
- **要求验证**：`HUMAN_CHECK_REQUIRED` 的挑战里，Cap 带 `method: "cap"` 和出题地址 `<CAP_ORIGIN>/<站点密钥>/scope/<范围>/`，页面直接去那里出题、交答案；Turnstile 的格式不变。
- **核验**：API 经服务绑定调 `siteverify`（不走公网），要求成功且范围对得上。Cap 服务本身出错、超时时放行并记录，和 Turnstile 的规则一样；凭证不对、用过、过期、不是这个红包的，就再要求一次验证。
- **能不能开**：Cap 要有地址（`CAP_ORIGIN`）、服务绑定、站点密钥和秘密密钥；缺了就不能选 Cap，已经选了的红包不再要求并记录错误，和 Turnstile 一样。
- **弹窗**：同一个弹窗。Cap 用我们自己的进度（扫光），算完自动继续。浏览器检测没过时说“这个浏览器没有通过检测，换个浏览器试试”；加载失败时可以重试。
- **资源**：Cap 的组件打进红包站的网页包，用到时才加载；WASM 和解压库也放在红包站自己的静态文件里，不用 CDN。
- **本地**：`bun run dev` 同时在 8788 端口跑 Cap，API 经开发注册表绑定到它；完整应用（full-app）把 Cap 放在 4187（本地体验）或 4188（测试）端口（4190 是浏览器禁用的端口，Safari 连不上）。
- **表单**：打开“领取前人机验证”后出现两张选择卡：Cap（默认）和 Cloudflare Turnstile，各写明代价。

## 4 消耗

服务器这边：按官方测试，出题约 3 微秒，核验题量加倍后约 0.5 毫秒；每次验证是出题、交答案、核验三次请求（交答案前浏览器还有一次预检），后两次各写一行。最近 7 天生产有 16,380 次领取提交，就算每次都验，一个月约 7 万次，远在 Workers Paid 已包含的额度里。服务绑定的调用不另收请求费。

用户那边：算题要花手机一点算力，见第 1 节。

## 5 发布

1. 先部署 Cap 服务，设好 `CAP_MASTER_SECRET`，配置里写上红包站这个站点。
2. 再发布 API（`CAP_ORIGIN`、服务绑定、站点密钥、`CAP_SECRET_KEY`）和网页。没有数据库迁移。

秘密密钥由脚本生成后直接存成 Worker 的密钥，配置里只写它的 SHA-256，不经过人手，也不打印。

## 6 以后（没做）

- `cap.lafi.sh` 托管组件和 WASM，给别的网站直接用（红包站自己的放在 hb.lafi.sh）。
- 量大时按凭证分片 Durable Object。
