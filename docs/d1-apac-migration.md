# D1 迁到亚太：步骤与回退

2026-10-17 草拟。2026-10-18 决定 D1 和 DO 一起迁到亚太，当天执行：00:36 发布准备阶段的代码，00:44–01:05 迁 Stage 并演练回退（第 2 节），01:35–01:39 切换生产，维护 3 分钟（记录见 [deployment-readiness.md](deployment-readiness.md)）。

## 1 先看数据

生产 D1 `hb-production` 的主库在美国西部（`running_in_region: WNAM`），没有读副本。建库时没有带位置参数，D1 默认把主库建在离发起建库请求最近的地方；建好后位置不能改，只能新建一个库再把数据搬过去。

DO 等 D1 的时间也算运行时长。生产 ActivityDO 在 10 月 11 日到 17 日的调用按所在大区汇总如下（Cloudflare DO 统计，按机房分组）：

| 大区 | 请求 | 占比 | 活跃时间 | 占比 | 平均每次 |
| --- | --- | --- | --- | --- | --- |
| 亚洲（HKG、NRT、SIN、KIX、ICN） | 6,997 | 54% | 22,401 秒 | 80% | 3.2 秒 |
| 美国西部（LAX、SJC、SEA） | 4,188 | 33% | 1,849 秒 | 7% | 0.44 秒 |
| 欧洲 | 1,248 | 10% | 3,416 秒 | 12% | 2.7 秒 |
| 美国中东部 | 441 | 3% | 212 秒 | 1% | 0.48 秒 |
| 合计 | 12,876 | | 27,885 秒 | | 2.2 秒 |

DO 建在第一个请求进来的机房。落在美国西部的那三分之一请求（很可能是绕道美国的国内用户）现在离 D1 很近。所以只搬 D1 不够：美国的 DO 会从平均 0.4–0.5 秒变成 2–3 秒，ActivityDO 总运行时长只少约两成。DO 要和 D1 一起搬（第 2 节第 2 步）：

- 新红包的 DO 一律建在亚太，和 D1 就近，按美国西部现在的水平估，平均每次 0.5 秒左右，运行时长约降到现在的两成；
- 落在亚洲的请求全程就近；落在美国的，每次请求多一次跨洋往返（约 100–200 毫秒），省下的是十几次跨洋查询；
- 已经存在的红包 DO 留在原地，直到红包结束：亚洲的立刻变快，美国的变慢，大多 24 小时内结束。

另一个方案是 D1 不动、新红包的 DO 建在美国西部。DO 开销同样能少约八成，也不用搬数据，但亚洲用户每次请求都要跨洋，页面读取也慢。2026-10-18 选了迁亚太。

MerchantDO（每个商户一个，按 LDC Client ID 命名，负责这个商户的全部付款）现在都在美国（SJC、SEA、DEN、LAX、DFW），因为叫醒它的付款队列和定时任务多在美国运行。它们现在紧挨着 D1，D1 搬走后每条查询都要跨太平洋，所以要一起迁（第 2 节第 2 步）。它们的时间主要花在调 Credit：最近 7 天从美国查单平均 0.72 秒、发款平均 1.1 秒。Credit 服务器在哪我们不知道，如果在亚洲，迁过去调 Credit 也会更快。

## 2 准备

代码部分已经写好，三个新配置默认关闭，随普通发布上线也不会改变任何行为。

1. **维护模式**：API 配置 `MAINTENANCE_MODE`，平时是 `"false"`（`apps/api/src/runtime/maintenance-mode.ts`）。改成 `"true"` 的版本只能带 `--maintenance` 发布：
   ```sh
   bun scripts/release.ts build|verify|deploy --env <环境> [--allow-live] --maintenance [--execute]
   ```
   打开后，四条写入路径都会停下；没有它，切换期间的写入会留在旧库里丢掉：
   - API：除 `/api/health` 外一律返回 503“系统维护中，请稍后再试。”；
   - 定时任务：整轮跳过；
   - 付款队列：消息 600 秒后重试。队列最多重试 5 次，能撑 50 分钟；就算有唤醒丢了，定时任务的付款兜底也会重新找到到期的付款；
   - ActivityDO 和 MerchantDO 的闹钟：顺延 60 秒。

   备份、诊断、付款许可和搬库这些运维脚本在维护中照常运行，只有发布需要 `--maintenance`。
2. **DO 跟着迁**：两项配置，平时都是空的（`apps/api/src/runtime/objects.ts`）。Cloudflare 不搬已经建好的 DO，位置提示也只在第一次创建时起作用。所以这两项在第 3 节第 7 步和换库同时改：那时维护开着、付款许可关着，不会有新 DO 建在别处。
   - `DO_LOCATION_HINT` 改成 `"apac"`：之后新建的 DO 都带亚太提示。已有的红包 DO 存着截止和开奖闹钟，名字不变，留在原地直到结束。
   - `DO_NAME_PREFIX` 改成 `"apac:"`：长期存在、不在 DO 里存数据的对象换名重建，旧的不再使用：
     - MerchantDO：每个商户一个，只存商户 ID 和下一次闹钟，付款状态和占用锁都在 D1；
     - 创建红包的串行器：每个作者一个；
     - 全局口令查找：每个用户一个；
     - 定时任务的维护协调：只有一个。

     各处取对象和身份校验都用同一套名字。旧 MerchantDO 的闹钟到点后只清理自己，不再运行。
3. **搬库脚本** `scripts/d1-move.ts`：
   - 不带 `--execute` 时只做检查，并列出要做的事。检查五项：
     - 目标库名必须是 `hb-<环境>-…`，并且不是当前库；
     - 目标库必须是空的；
     - 目标库必须在亚太；
     - 线上必须已处于维护模式；
     - 生产的三项付款许可必须已关。
   - 带 `--execute` 时，记下旧库的 Time Travel 书签，把表结构和数据分别导出到私有目录（`.wrangler/backups`），组装成导入文件，再导入目标库。不能直接导入完整导出：
     - D1 一直检查外键，大文件的导入又是分几次提交的，`PRAGMA defer_foreign_keys` 管不到整个文件；
     - 完整导出按建表先后排列，每张表后面紧跟它的数据，而有 11 张表引用了比它晚建的表（比如 `sessions` 引用 `users`）。

     所以导入文件先建全部表，再按外键依赖先导被引用的行，最后建索引和触发器，导入时不会触发任何触发器。数据导出每条语句占一行（值里的换行写成 `char(10)`），不是这样的导出直接拒绝。
   - 导入后再按同样方式导出新库的数据，必须和旧库的逐字节相同；另外逐表比较行数，按类型比较表、索引和触发器的数量（现在是 35 张表、61 个索引、74 个触发器、28 个迁移）。有任何差异就以非零状态退出。
   - `--compare-only` 只做比较。
4. **建新库**：
   ```sh
   npx wrangler d1 create hb-staging-apac --location apac
   npx wrangler d1 create hb-production-apac --location apac
   ```
   用 `wrangler d1 info` 确认 `running_in_region` 是 APAC。位置参数只是尽力而为，如果落到别处就停下重新评估。

   2026-10-18 已建好，两个都在 APAC：`hb-staging-apac`（`20bb686f-9bc8-4990-be54-18097c992df5`）和 `hb-production-apac`（`c4603fec-188e-4021-bb07-9ff97a49b249`）。
5. **Stage 演练**：2026-10-18 00:44–01:05 照第 3 节走完，并演练了第 4 节的无损回退。演练发现三处会让生产切换失败的问题，都已修好：
   - 维护模式下备份、诊断、付款许可和搬库脚本都拒绝运行，带 `--maintenance` 也构建不了；
   - 完整导出直接导入时报 `no such table: main.users`；只把建表提前，又因分批提交报外键失败（改法见上面第 3 项）；
   - 比较行数用了 35 项的 `UNION ALL`，D1 的复合查询最多 5 项。

   修好后的一遍：开维护的发布 22 秒，旧库备份 7 秒，搬库 45 秒，切库的发布 20 秒，维护中验证约 20 秒，关维护的发布 21 秒，合计约 3 分钟。新库的完整导出和搬库前旧库的导出 SHA256 相同，`wrangler d1 migrations list` 显示没有待执行的迁移，发布工具接受新库的名字和 ID。回退时配置改回旧库、两项 DO 配置清空，带 `--maintenance` 发布后，旧库导出的 SHA256 仍和搬库前相同；再切回新库后关维护。Stage 现在用 `hb-staging-apac`，DO 带亚太提示和 `apac:` 前缀。

   维护期间网页顶栏显示“身份检查失败，重试”，没有说明在维护。
6. **选时段**：选用户最少的时段，另外要满足：
   - 窗口前后 30 分钟内没有红包截止，也没有限时开奖到点（查 D1）；
   - 发布前诊断里没有在途发送、结果未知或商户占用。

## 3 切换步骤（生产，2026-10-18 已执行）

0. **发布前检查**：和平时一样，记下诊断结果、付款开关版本、API 和 Web 的当前版本号。
1. **暂停付款**：用 CAS 关闭三项付款许可。
2. **开维护**：把 `MAINTENANCE_MODE` 改成 `"true"`，带 `--maintenance` 发布，这时库还是旧库。确认健康检查正常、其他接口返回 503，再等 30 秒，让在途请求处理完。
3. **旧库留底**：运行 `payment-backup.ts --remote-export`，在本地隔离恢复，记下各表行数和 SHA256。
4. **搬库**：
   ```sh
   bun scripts/d1-move.ts --env production --target hb-production-apac            # 检查
   bun scripts/d1-move.ts --env production --target hb-production-apac --execute  # 书签、导出、导入、比较
   ```
   导出期间旧库会阻塞其他请求，维护中没有影响。比较有任何差异就停在这里，按第 4 节回退。
5. **切绑定和 DO**：改 `apps/api/wrangler.production.jsonc`：`database_name`、`database_id` 指向新库（`hb-production-apac`、`c4603fec-188e-4021-bb07-9ff97a49b249`），`DO_LOCATION_HINT` 改成 `"apac"`，`DO_NAME_PREFIX` 改成 `"apac:"`，`MAINTENANCE_MODE` 仍是 `"true"`。然后带 `--maintenance` 构建、校验、部署。
6. **维护中验证**：
   - `payment-backup.ts --remote-export` 这时导出的是新库。维护中两个库都没有写入，所以它的 SHA256 必须和第 3 步旧库的导出相同；在本地恢复后，完整性和外键检查通过；
   - `wrangler d1 migrations list` 对新库显示没有待执行的迁移。
7. **关维护**：`MAINTENANCE_MODE` 改回 `"false"`，正常发布。
8. **恢复付款**：诊断干净后，用 CAS 恢复三项许可。
9. **发布后检查**：
   - 和平时一样核对健康检查、构建标记、旧域名跳转、启动检查、推送握手和红包页；
   - 一天后用 DO 统计按机房对比平均运行时长，看是否符合第 1 节的估算。
10. **记录**：在 `deployment-readiness.md` 写发布记录，更新环境资源表；本文改成“已执行”。

## 4 回退

- **关维护之前（第 1–6 步）**：随时可以无损回退。配置改回旧库，`DO_LOCATION_HINT`、`DO_NAME_PREFIX` 改回空，带 `--maintenance` 发布；然后关维护、恢复付款。旧库在导出后没有任何写入，数据不丢；旧名字的对象也都还在原地。
- **关维护之后**：新的领取、付款都写在新库里。
  - 小问题直接在新库上修，不切回去。直接把配置改回旧库会丢掉切换后的所有新数据。
  - 必须回到美国西部时，就反向再迁一次：新建一个 `--location wnam` 的库，按第 3 节从新库搬过去；`DO_LOCATION_HINT` 改成 `"wnam"`，`DO_NAME_PREFIX` 换一个新前缀。
- **付款安全**：切换期间三项付款许可一直关着；核对有任何疑问就不恢复。
- **保留期**：旧库保留 30 天（与 Time Travel 的保留期相同），`hb-staging` 和 `hb-production` 都保留到 2026-11-17，确认稳定后再删。迁移前后的书签都记进发布记录。
