# D1 迁到亚太：步骤与回退

2026-10-17 草拟，尚未执行。

## 1 先看数据

生产 D1 `hb-production` 的主库在美国西部（`running_in_region: WNAM`），没有读副本。建库时没有带位置参数，D1 默认把主库建在离发起建库请求最近的地方；建好后位置不能改，只能新建一个库再把数据搬过去。

DO 等 D1 的时间也算运行时长。生产 ActivityDO 在 10 月 11 日到 17 日的调用按所在大区汇总如下（Cloudflare DO 统计，按机房分组）：

| 大区 | 请求 | 占比 | 活跃时间 | 占比 | 平均每次 |
| --- | --- | --- | --- | --- | --- |
| 亚洲（HKG、NRT、SIN、KIX、ICN） | 6,997 | 54% | 22,401 秒 | 80% | 3.2 秒 |
| 美国西部（LAX、SJC、SEA） | 4,188 | 33% | 1,849 秒 | 7% | 0.44 秒 |
| 欧洲 | 1,248 | 10% | 3,416 秒 | 12% | 2.7 秒 |
| 美国中东部 | 441 | 3% | 212 秒 | 1% | 0.48 秒 |
| 合计 | 12,876 | | 27,885 秒 | | 2.2 秒 |

DO 建在第一个请求进来的机房。落在美国西部的那三分之一请求（很可能是绕道美国的国内用户）现在离 D1 很近。D1 搬到亚太后：

- 亚洲的 DO 变快：按美国西部现在的水平估，平均从 3.2 秒降到 0.5 秒左右；
- 美国的 DO 变慢：每条查询改为跨太平洋，平均从 0.4–0.5 秒升到 2–3 秒；
- 欧洲变化不大，可能略慢。

粗估 ActivityDO 总运行时长只少约两成。对用户来说，落在亚洲的一半多请求变快，落在美国的三分之一多请求变慢。MerchantDO 现在都在美国（SJC、SEA、DEN、LAX、DFW），对它们也是变慢。

另一个选择见第 5 节：新红包的 DO 指定建在 D1 附近。估算 ActivityDO 时长能少约八成，几乎所有请求都会变快，而且不用搬数据。**建议先比较两个方案，再决定是否执行下面的迁移。**

## 2 准备（提前完成，不影响线上）

1. **维护开关**：这次要新写代码，默认关闭，先正常发布一次。API 配置加变量 `MAINTENANCE_MODE`，打开时：
   - API 除 `/api/health` 外一律返回 503“系统维护中，请稍后再试”；
   - 定时任务直接跳过；
   - 付款队列的消息全部 60 秒后重试；
   - ActivityDO 和 MerchantDO 的闹钟顺延 60 秒。

   这样用户请求、定时任务、付款队列和 DO 闹钟这四条写入路径都会停下。没有它，切换期间的写入会留在旧库里丢掉。发布工具要允许维护版本单独发布，测试要覆盖上面四点。
2. **核对脚本**：对两个库逐表 `COUNT(*)`，比较触发器数量和已执行的迁移数量（现在是 37 张表、74 个触发器、28 个迁移）。
3. **建新库**：
   ```sh
   npx wrangler d1 create hb-staging-apac --location apac
   npx wrangler d1 create hb-production-apac --location apac
   ```
   用 `wrangler d1 info` 确认 `running_in_region` 是 APAC。位置参数只是尽力而为，如果落到别处就停下重新评估。
4. **Stage 演练**：在 Stage 完整走一遍第 3 节，再演练一次第 4 节的回退，记下每步耗时。重点确认三件事：
   - 导出文件里触发器建在数据之后，导入时不会被触发；
   - `d1_migrations` 表随导出带过去，新库 `wrangler d1 migrations list` 显示没有待执行的迁移；
   - 发布工具对新库的名字和 ID 校验通过。
5. **选时段**：选用户最少的时段，另外要满足：
   - 窗口前后 30 分钟内没有红包截止，也没有限时开奖到点（查 D1）；
   - 发布前诊断里没有在途发送、结果未知或商户占用。

## 3 切换步骤（生产，维护约 15 分钟）

0. **发布前检查**：和平时一样，记下诊断结果、付款开关版本、API 和 Web 的当前版本号。
1. **暂停付款**：用 CAS 关闭三项付款许可。
2. **开维护**：发布 `MAINTENANCE_MODE=true` 的版本，库仍是旧库。确认健康检查正常、其他接口返回 503，再等 30 秒，让在途请求处理完。
3. **旧库留底**：记下旧库的 Time Travel 书签；运行 `payment-backup.ts --remote-export`，在本地隔离恢复，记下各表行数和 SHA256。
4. **导出**：
   ```sh
   npx wrangler d1 export hb-production --remote --output=<私有目录>/prod-cutover.sql
   ```
   导出期间旧库会阻塞其他请求，维护中没有影响。
5. **导入**：
   ```sh
   npx wrangler d1 execute hb-production-apac --remote --file=<私有目录>/prod-cutover.sql
   ```
6. **核对新库**：
   - 核对脚本逐表比较，行数、触发器数、迁移数都要和旧库一致；
   - 新库再导出一次，用备份工具在本地恢复，完整性和外键检查通过，用户、红包、领取、报名、付款任务的数量和第 3 步一致；
   - 任何一项对不上就停在这里，按第 4 节回退。
7. **切绑定**：把 `apps/api/wrangler.production.jsonc` 的 `database_name` 和 `database_id` 改成新库，构建、校验，然后部署。维护开关仍然开着。
8. **维护中验证**：`wrangler d1 info` 看两个库，新库开始有读写，旧库不再有写入。用 `wrangler d1 execute` 对新库做几条只读查询。
9. **关维护**：发布 `MAINTENANCE_MODE=false` 的版本。
10. **恢复付款**：诊断干净后，用 CAS 恢复三项许可。
11. **发布后检查**：
    - 和平时一样核对健康检查、构建标记、旧域名跳转、启动检查、推送握手和红包页；
    - 一天后用 DO 统计按机房对比平均运行时长，看是否符合第 1 节的估算。
12. **记录**：在 `deployment-readiness.md` 写发布记录，更新环境资源表；本文改成“已执行”。

## 4 回退

- **关维护之前（第 1–8 步）**：随时可以无损回退。把配置改回旧库，部署（维护仍开），然后关维护、恢复付款。旧库在导出后没有任何写入，数据不丢。
- **关维护之后**：新的领取、付款都写在新库里。
  - 小问题直接在新库上修，不切回去。直接把配置改回旧库会丢掉切换后的所有新数据。
  - 必须回到美国西部时，就反向再迁一次：开维护，从新库导出，导入一个新建的 `--location wnam` 库，核对后切绑定。步骤和第 3 节相同。
- **付款安全**：切换期间三项付款许可一直关着；核对有任何疑问就不恢复。
- **保留期**：旧库保留 30 天（与 Time Travel 的保留期相同），确认稳定后再删。迁移前后的书签都记进发布记录。

## 5 备选：新红包的 DO 建在 D1 附近

取 ActivityDO 时带上位置提示 `{ locationHint: "wnam" }`，让新建的 DO 落在 D1 附近。用一个公共函数替换所有 `ACTIVITY_DO.get(...)`，保证第一次创建时就带上提示。

- **开销**：每条 D1 查询只要几毫秒。按美国西部现在 0.44 秒的平均值估算，ActivityDO 运行时长约降到现在的两成。
- **延迟**：落在亚洲和欧洲的用户，每次请求多一次到美国的往返（约 100–200 毫秒），但省下的是十几次跨洋查询，整体仍然快得多；推送晚到约 150 毫秒。落在美国的用户不变。
- **范围**：只影响新红包，已经建好的 DO 留在原地，直到红包结束。全局查找和维护用的 DO 也可以一并带上提示。
- **成本**：不搬数据，不停服，代码改动小，可以随普通发布上线。
- **将来**：如果页面读取（Worker 读 D1）也要变快，再考虑 D1 读副本。
